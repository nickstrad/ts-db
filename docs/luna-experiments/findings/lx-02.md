# lx-02: DuckDB analysis query benchmark

Date: 2026-10-11

Script: [`work-scripts/deno/lx-02-query-bench.ts`](../../../work-scripts/deno/lx-02-query-bench.ts)

## Method

The benchmark populated the item-21 event tables with deterministic synthetic rows, split across all eight
tables at the weights in the script. The requested scale is the total row count across those tables. It ran
all eight starter SQL files and the ten item-23 catalog queries. The benchmark warmed each successful query
once, then reported the median of three timed calls. Timings are wall-clock milliseconds for execution plus
fetching results into the Deno client. EXPLAIN plans are ordinary `EXPLAIN`, not `EXPLAIN ANALYZE`.

The first 12M-row ingest was OOM-killed during ingestion. To bound memory while preserving the query workload,
I changed the harness to insert in 50,000-row ranges, use a disk-backed DuckDB database, limit DuckDB to one
thread and 1 GB, and generate the JSONL fixture with DuckDB's COPY writer rather than JavaScript row objects.
I ran 1M and 12M as separate invocations with three repeats each. Both final invocations completed. The
earlier unbatched 12M attempt did not produce usable timings.

Commands:

```sh
deno run -A work-scripts/deno/lx-02-query-bench.ts --rows 1000000 --repeats 3 --batch-rows 50000
deno run -A work-scripts/deno/lx-02-query-bench.ts --rows 12000000 --repeats 3 --batch-rows 50000
```

These are synthetic, full-window workloads on a shared VM, not production traces. The timestamp predicate
covered the generated month, so it did not test narrow-window selectivity. Results include client-side
materialization and may vary with VM contention.

`starter:trace-timeline.sql` fails with
`Malformed JSON ... Input: "/api/7" when casting from source column extra`: the UNION's `extra` column
combines `http_events.path` with JSON-valued `k6_points.tags`, and DuckDB resolves the shared type as JSON.
Cast the path (and other textual extras) explicitly to `VARCHAR`, or cast every arm of `extra` to one
deliberate common type.

`catalog:k6-vs-platform` fails because this DuckDB build has no `date_bin` scalar function. Use a supported
bucket expression (for example, verify `time_bucket(INTERVAL '10 seconds', ts)` on the pinned build) and
retain the same timestamp origin/alignment semantics.

## Slowest queries and EXPLAIN evidence at 12M

1. **`starter:lifecycle-events.sql` — 6,258.204 ms.** EXPLAIN shows `SEQ_SCAN lifecycle_events` projecting
   `ts, role, pid, phase, detail`, followed by `WINDOW` for
   `LAG(ts) OVER (PARTITION BY role, pid ORDER BY ts)`, then `ORDER_BY role, pid, ts`. This is a full table
   scan plus partition ordering/window work and a final ordered output.
2. **`catalog:handler-throughput` — 4,484.777 ms.** EXPLAIN shows `SEQ_SCAN platform_events` with only
   `kind='handler'` filtering, projecting `ts, app_id, name, outcome`; it estimates 900,000 qualifying rows. A
   hash aggregation groups by minute, app, handler, and outcome, then the query sorts by minute/app/handler.
   The high-cardinality time grouping and sort dominate after the scan.
3. **`starter:log-level-distribution.sql` — 2,865.064 ms.** EXPLAIN shows `READ_JSON` over the full 12M-line
   file projecting only `level`, then `HASH_GROUP_BY`, a window for the total, and ordering. This is a full
   file parse and aggregate; the plan's group cardinality estimate (~7.59M) is far above the fixture's three
   actual levels, so treat that estimate as inaccurate.

At 1M, the same lifecycle and JSONL queries were also the two slowest (474.163 ms and 268.154 ms);
`catalog:slowest-sql` was third at 179.054 ms. At 12M, `handler-throughput` overtook both that catalog query
and JSONL distribution.

## Guidance for item 23

- **Fix executability before freezing the catalog.** Make `trace-timeline`'s UNION column types explicit and
  replace `date_bin` with a function supported by the pinned DuckDB version. Add a small execution check for
  every catalog query against the item-21 DDL so unsupported functions and type coercions fail before release.
- **Keep the time predicate sargable and narrow scans.** Continue using half-open timestamp bounds
  (`ts >= start AND ts < end`) and select only columns needed by each analysis. This run used a full-month
  window, so it cannot quantify gains from narrower windows. Preserve useful timestamp ordering during
  ingestion and validate actual zone-map pruning with a selective-window `EXPLAIN ANALYZE` before recommending
  physical layout changes.
- **Lifecycle needs ordered window processing.** `lifecycle-events` outputs every matching row and computes a
  per-process lag, so a full-window request inherently reads and sorts much of the table. Keep the
  partition/order keys `(role, pid, ts)` aligned with the window and final ordering, offer a time-bounded
  option, and consider a maintained summary only if this query is frequent. Do not assume a conventional
  secondary index will remove the window/sort cost in DuckDB.
- **Handler throughput can benefit from pre-aggregation for repeated dashboards.** Its grouping by
  minute/app/name/outcome yields many groups. If item 23 serves repeated historical dashboard requests,
  consider hourly/minute rollups at ingest or a cache; otherwise keep the one-off aggregate and avoid extra
  storage/index write cost. The `kind='handler'` predicate is selective only to the synthetic 75% of platform
  rows, so it does not justify an ART index by itself.
- **Treat JSONL level counts as an ad hoc file scan.** Reading only `level` avoids decoding unused fields, but
  all lines still need parsing. For recurring analysis, ingest the level into a typed table or maintain counts
  during logging/rotation. Keep the direct JSON query for one-off inspection.
- **Avoid adding DuckDB ART indexes solely from this benchmark.** The plans show analytical scans, groupings,
  and window sorts; this workload does not demonstrate a selective point lookup that would benefit from an ART
  index. Measure narrower time windows and real cardinalities first; prioritize ordering/partitioning,
  rollups, or query limits based on that evidence.
