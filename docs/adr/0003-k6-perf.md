# ADR 0003: k6 for a perf/smoke harness against the live HTTP API

## Status

Accepted.

## Context

The repo has no automated check that exercises the server's HTTP surface end-to-end under load,
distinct from the functional multi-process integration test (`deno task integration`). We want a
lightweight, repeatable way to replay the demo call order against a running server and catch
regressions in latency or error rate, without pulling a load-testing framework into the TypeScript
dependency graph or touching `core/`, `platform/`, or `sdk/` (this item is explicitly
TypeScript-free and concurrent with the Effect-TS port work in item 02).

## Decision

Use [k6](https://k6.io) (Grafana), installed as a standalone binary at `/usr/local/bin/k6`
(v0.56.0, see `perf/README.md` for the exact tarball URL), driven entirely by its own JS scripting
API. k6 scripts are not Deno/Node modules and don't go through `deno.json`'s `imports` map, so they
stay outside the TypeScript/Effect port entirely while still living in this repo as `perf/smoke.js`
and `perf/lib/api.js`.

### Smoke scenario

`perf/smoke.js` runs 1 VU for 30s, repeating the exact call order from `scripts/demo.ts`:
`createGame` → `getGame` → 5x `makeMove` → `winsByMark`. Each iteration creates its own game
(unique `xPlayer`/`oPlayer` per VU/iteration), so iterations are independent and never collide on
`expectedVersion`. Every request carries `X-Trace-Id: <vu>-<iter>-<run-id>` so a request can be
correlated back to a specific k6 iteration in server logs later.

Thresholds (`http_req_failed` rate < 1%, `http_req_duration` p(95) < 250ms, `checks` rate == 100%)
are deliberately generous for a single-VU smoke check: the goal is "did the whole call chain work
and stay responsive," not a load ceiling.

### Server-down must fail loudly

A smoke test that silently passes when the server is unreachable is worse than no test. k6 always
counts connection-level failures (refused connections, timeouts) in `http_req_failed` regardless
of any response-status configuration, and `perf/lib/api.js` additionally calls
`http.setResponseCallback(http.expectedStatuses(200))` so non-200 API responses (e.g. a 400 from a
rejected mutation) count as failures too. Either case drives `http_req_failed` and `checks` past
their thresholds, so k6's own threshold-failure exit code (non-zero) is the failure signal — no
extra "is the server up" probe was needed.

### Output location

Raw per-request output (`k6 run --out json=...`) and the `handleSummary`-written summary JSON land
under `logs/k6/<run-id>/`, which is gitignored. This keeps perf run artifacts out of version
control (they're regenerated per-run, not reviewed as diffs) while giving workstream 5's planned
log ingestion/analysis tooling (see `docs/plans/effect-port-and-observability.md`) a stable,
discoverable path to join against, using the same `<run-id>` that tags each request's
`X-Trace-Id`.

## Not a benchmark claim

Per the repo README's "Deliberate limits" section, this prototype has one writer connection per
app and one shared serial reader process — "enough to expose the design, not to establish
capacity." `perf/smoke.js` is a functional regression check (did the call chain work, did latency
stay sane for one VU), not a throughput or capacity benchmark. `perf/README.md` repeats this
caveat so it travels with the scripts.

## Consequences

- No new TypeScript/npm dependency; k6 is an external binary dependency recorded in the knowledge
  store and in `perf/README.md`'s install recipe, not in `deno.json`.
- Future load/query/mixed scenarios (`perf/mutation_load.js`, `perf/query_load.js`,
  `perf/mixed.js` — already wired as `deno task perf:load`/`perf:query`/`perf:mixed` in
  `deno.json`) can reuse `perf/lib/api.js`'s helpers and the same `logs/k6/<run-id>/` convention.
- Because k6 scripts run outside Deno, they can't import `sdk/client.ts` directly; `perf/lib/api.js`
  re-implements the same request shape (route, auth header, JSON envelope) by hand and must be kept
  in sync with `platform/server.ts` if the route or envelope ever changes.
