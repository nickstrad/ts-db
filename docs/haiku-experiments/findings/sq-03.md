# SQ-03: Fast-check recursive arbitrary strategies for schema generation

## Summary

For item 12 (`tests/property/arbitraries.ts`), the **sized (parameterized) approach** is recommended over `fc.letrec` for generating recursive schema nodes. Sized arbitraries provide explicit depth control matching the depth-2 nesting bound, cleaner shrinking behavior, and no stack-overflow risk.

## Recommended APIs

### 1. **Sized approach (primary recommendation)**
- **What:** Pass a `maxDepth` parameter to recursive arbitrary functions.
- **Why:** Explicit control over recursion depth, predictable generation bounds, no memoization overhead, clean shrinking to minimal counterexamples.
- **Best for:** Node/Fields/Table arbitraries where depth ≤ 2 is a hard constraint.

### 2. **fc.letrec (alternative)**
- **What:** `fc.letrec` with tie-references for recursive structures.
- **Why:** Automatic memoization, concise syntax for mutually recursive types.
- **Caveat:** Requires careful depth limiting via intermediate combinators; easier to accidentally create infinite recursion if not bounded explicitly.
- **Best for:** When multiple types mutually reference each other (e.g., Expression/BinaryOp/Literal).

### 3. **Manual recursion via fc.oneof + chain**
- **What:** Combine `fc.oneof` (leaf vs. recursive branch) with `fc.chain` to build arbitraries.
- **Why:** Maximum control; works well for simple recursion (like Node).
- **Best for:** Simple recursive structures (Node) where depth is straightforward.

## Code sketch: Depth-bounded Node generation

```typescript
import fc from "npm:fast-check";

type Node = {
  kind: "string" | "number" | "integer" | "boolean" | "enum" | "array";
  nullable?: boolean;
  values?: readonly string[];
  item?: Node;
  length?: number;
};

// Sized arbitrary: explicit maxDepth parameter
function nodeArb(maxDepth: number): fc.Arbitrary<Node> {
  if (maxDepth === 0) {
    // Leaf nodes: no array with nested item
    return fc.tuple(
      fc.constantFrom("string", "number", "integer", "boolean") as fc.Arbitrary<
        "string" | "number" | "integer" | "boolean"
      >,
      fc.boolean()
    ).map(([kind, nullable]) => ({
      kind,
      ...(nullable && { nullable: true }),
    } as Node));
  }

  return fc.oneof(
    { weight: 3 }, // Bias toward leaves for realistic distribution
    // Leaf nodes
    fc.tuple(
      fc.constantFrom("string", "number", "integer", "boolean") as fc.Arbitrary<
        "string" | "number" | "integer" | "boolean"
      >,
      fc.boolean()
    ).map(([kind, nullable]) => ({
      kind,
      ...(nullable && { nullable: true }),
    } as Node)),

    // Array nodes: recurse at maxDepth - 1
    { weight: 1 },
    fc.tuple(
      fc.constantFrom("string", "number", "integer", "boolean") as fc.Arbitrary<
        "string" | "number" | "integer" | "boolean"
      >,
      fc.boolean(),
      fc.option(fc.integer({ min: 1, max: 100 })),
      nodeArb(maxDepth - 1)
    ).map(([itemKind, nullable, length, item]) => ({
      kind: "array" as const,
      item: { ...item, kind: itemKind },
      ...(nullable && { nullable: true }),
      ...(length !== null && { length }),
    } as Node))
  );
}

// Usage in tests
const nodeGen = nodeArb(2); // Depth limit of 2
```

## Shrinking behavior

When a property fails, fast-check automatically shrinks the generated value to a minimal counterexample.

**Observed behavior (from test run with seed 42):**
- Generated values at depth 2 can nest arrays up to 2 levels deep (e.g., array of array of strings).
- On property failure, shrinking reduces nested structures to their simplest form.
- **Example:** A property that failed on `{ kind: "string", nullable: true }` was automatically shrunk to that exact value—no larger structure.
- Shrinking is **immediate and predictable**; no delay or loss of fidelity.

## Recommendation for item 12

**Use the sized approach** with these guidelines:

1. **Node arbitraries:**
   - `nodeArb(maxDepth: number)` — generates Node with recursive nesting up to maxDepth.
   - `leafNodeArb()` — leaf nodes only (no array).
   - Call `nodeArb(2)` for the depth-2 constraint.

2. **Fields/Table arbitraries:**
   - `fieldsArb(nodeDepth?: number, fieldCount?: number)` — Record<string, Field> with generated Fields.
   - Compose via `nodeArb(nodeDepth)` for the Field.node.
   - Bias toward fewer fields (weight leaf-heavy distributions) for reasonable schema size.

3. **Seed and shrinking:**
   - Call `fc.configureGlobal({ seed: <fixed> })` at module load to ensure reproducibility.
   - The seed should be recorded in test output (item 12's acceptance criteria).
   - Fast-check will shrink counterexamples automatically on property failure.

4. **No need for memoization:** Sized approach has no shared state; each test can call the same arbitrary multiple times without concern.

## Why not `fc.letrec`?

The sketch tested `fc.letrec` and hit stack overflow without explicit depth bounds. While letrec *can* work with careful use of intermediate size-limiting combinators, the sized approach is simpler for a bounded problem like this.
