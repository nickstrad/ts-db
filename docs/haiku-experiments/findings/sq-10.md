# SQ-10: Postgres driver bake-off for MT-03

**Measurement date**: 2026-10-11
**Model**: `claude-haiku-5-5` (resolved: `claude --model haiku -p "Reply with the word ok." --output-format json` reported `modelUsage` keys `['claude-haiku-5-5']`)
**Postgres**: `PostgreSQL 17.11 (Debian 17.11-1.pgdg13+2) on x86_64-pc-linux-gnu`, Docker container `sq10-pg` on `127.0.0.1:5433`
**Drivers**: `npm:postgres@3.4.9`, `npm:pg@8.23.1` (latest published at run time; exact pins)
**Deno**: `deno 2.9.5`

## Recommendation

**Pin `npm:postgres@3.4.9` for MT-03.** Justification paragraph for the MT-03 code comment (cite verbatim):

> Driver pin: `npm:postgres@3.4.9` (porsager/postgres), not `npm:pg`. sq-10 measured both on the registry's own workload (PK SELECT, api_keys→tenants join by key_hash, UPDATE/DELETE by PK, 100-row batch INSERT, BEGIN/COMMIT) and latency was within run-to-run noise (PK SELECT median 0.46–1.17 ms for both drivers across four runs; see `docs/haiku-experiments/findings/sq-10.md`). The choice therefore rests on the transaction and error surface: `sql.begin` rolled back a thrown error with the row absent (verified), the equivalent `npm:pg` path needed a hand-written BEGIN/ROLLBACK/release wrapper, and server errors arrive as a named `PostgresError` with the SQLSTATE in `code` (23505 on duplicate slug, verified). Pinned exactly; a version bump must re-run `work-scripts/deno/sq-10-pg-bench.ts`.

Caveat the MT-03 builder must check, **not verified here**: if MT-08 (Better Auth) requires a `pg` `Pool` instance, the single-driver rule forces that decision to be made in MT-08, not by mixing drivers in MT-03.

## Test-layer verdict

**pg-mem: NO — not sufficient for MT-03's tests.** Real ephemeral Postgres (the MT-01 compose service) is required for the registry.

- **First failing feature**: `REFERENCES <table>` with no column list, which is the plan's own `api_keys.tenant_id` DDL. pg-mem fails to parse it:

  ```
  FAIL  CREATE TABLE api_keys (id uuid PRIMARY KEY, tenant_id uuid REFERENCES tenants, key_hash text UNIQUE)
        -> 💔 Your query failed to parse.
  OK    CREATE TABLE api_keys (id uuid PRIMARY KEY, tenant_id uuid REFERENCES tenants(id), key_hash text UNIQUE)
  ```

  With that one token changed (`REFERENCES tenants(id)`), every other registry statement passed, so the rest of the verdict is about pg-mem's behavior beyond this parse gap.

- **Most serious failure (silent)**: ROLLBACK does not roll back. A rolled-back insert stays visible:

  ```
  client BEGIN/ROLLBACK -> rows visible: 1
  after error + ROLLBACK -> rows visible: 2
  ```

  Any MT-03 test that relies on rollback (for example, an `issueApiKey` atomicity test) would pass or fail for the wrong reason under pg-mem. This is the reason for the NO.

- **Secondary fidelity issue**: a duplicate `slug` (a `UNIQUE` column) is reported by pg-mem as a violation of `tenants_pkey`:

  ```
  PASS  unique violation surfaces code 23505  -- code=23505 msg=ERROR: insert into "tenants" ... duplicate key value violates unique constraint "tenants_pkey"
  ```

  The 23505 SQLSTATE is correct, but the constraint name is not. Tests must not assert on constraint names under pg-mem.

### Suspicious-number checks (per the brief)

1. **Run order.** Postgres-first (run1) and pg-first (run2) agree on reads (SELECT medians 0.46–0.59 ms in both). Writes shifted by a few ms in both directions, so order has no material effect on the verdict.
2. **Pool peak = 1 in run3.** Run3 reported `peakActiveDuring20WayBurst: 1` for postgres, which conflicted with run1's 10. I judged it a sampling artifact: the probe took a single sample at 150 ms, during pool warm-up. That is a hypothesis I did not confirm. I changed the probe to poll every 50 ms and keep the maximum. The final run reports 10 for both drivers.
3. **pg TXN p99 = 217 ms (final).** A tail outlier on a shared, loaded host. Not re-run beyond the four runs above.

### Pooling and connection behavior

Both drivers were configured with `max: 10` (postgres.js `max`, `pg.Pool` `max`). Pooling probe output from the final run:

```
"pool": { "peakActiveDuring20WayBurst": 10, "clientBackendsAfterBurst": 10 }   // postgres
"pool": { "peakActiveDuring20WayBurst": 10, "clientBackendsAfterBurst": 10 }   // pg
```

Cold connect plus first query (`coldConnectFirstQueryMs`, one sample per run, noisy): postgres 502.27 (run1), 131.3 (final); pg 28.88 (run1), 69.84 (final). Not a basis for any decision.

### Transaction sanity (final run)

Both drivers: `commitVisible: true`, `rollbackThrew: "rollback-probe"`, `rollbackRowVisible: false`. postgres.js `sql.begin` rolled back a thrown error. The `pg` path needs an explicit `BEGIN` / `ROLLBACK` / `release` wrapper, which the bench implements.

### Error ergonomics (final run)

```
postgres: { "ctor": "PostgresError", "name": "PostgresError", "code": "23505", "constraint": "tenants_slug_key" }
pg:       { "ctor": "DatabaseError",  "name": "error",          "code": "23505", "constraint": "tenants_slug_key" }
syntax:   postgres code 42601 / pg code 42601, both with the message "syntax error at or near \"SELEC\""
```

Both expose the 5-character SQLSTATE in `code` and the constraint name. postgres.js gives a self-describing `PostgresError` name; `pg` reports `name: "error"`, so `instanceof` checks or name-based matching are less direct with `pg`.

### Connection-setup size (measured from the bench's adapters)

- `openPostgres()` (connection, query, transaction): 11 lines.
- `openPg()` (pool, query, transaction wrapper, release): 27 lines.

## Deno friction

**postgres (3.4.9):** no npm-compat warnings in the bench output (stderr checked with `grep -v Initialize|Download`). Ran under the narrow permission set below.

**pg (8.23.1):** reads every `PG*` environment variable at `Client` construction. Under a narrow `--allow-env` allow-list, the bench failed:

```
error: Uncaught (in promise) NotCapable: Requires env access to "PGBINARY", run again with the --allow-env flag
    at new ConnectionParameters (.../node_modules/.deno/pg@8.23.1/node_modules/pg/lib/connection-parameters.js:15:25)
```

Full `--allow-env` is required for `npm:pg`. Narrowed permission set that passes end to end (`deno run --no-lock --allow-net=127.0.0.1 --allow-env --allow-read --allow-write`, exit 0, `SQ10_ITERS=200`):

```
| SELECT tenant by PK (prepared/named) | postgres | 200 | 1.003 | 6.727 |
| SELECT tenant by PK (prepared/named) | pg | 200 | 2.158 | 8.561 |
```

**Lockfile side effect:** the first `deno run` modified `deno.lock` (+`npm:pg@8.23.1`, +`npm:postgres@3.4.9`, plus transitive entries). Not in the sq-10 allowed set, so I reverted it with `git checkout -- deno.lock`. Future runs use `--no-lock`. The lock entries are MT-03's to create. The diff is kept at `/tmp/sq10/deno.lock.diff`.

**pg-mem:** `deno run` needed `--node-modules-dir=auto` for a scratch file outside a project (`Could not find a matching package for 'npm:pg-mem@3.0.14' in the node_modules directory`). pg-mem also prints a deprecation warning for its own transitive `whatwg-encoding`.

**Type check:** `deno check --no-lock` on the bench first flagged an implicit `any` in the pg adapter (TS7006); fixed, and the file now passes `deno check` and `deno fmt --check`.

## Honest limits (not tested)

- **MT-08 / Better Auth compatibility** with either driver: *not executed*. The recommendation's caveat depends on it.
- **MT-01 compose service and `make db-migrate`**: *not executed*. MT-01 has not landed; I applied the DDL myself with `psql`.
- **Narrow permissions for `npm:postgres` in isolation**: *not executed*. The `--allow-env` failure was from `npm:pg`; the narrow set was verified only with the full bench, which runs both drivers.
- **pg-mem beyond the listed statements**: *not executed*: `ON CONFLICT`, `RETURNING *`, multi-table joins beyond the one used, `LIKE`, `ORDER BY`/`LIMIT` pagination, `SELECT ... FOR UPDATE`, and any `\dt`-style introspection beyond `information_schema.tables`.
- **Concurrency and isolation**: *not executed*. No concurrent writers, no isolation-level tests, no lock contention.
- **Network latency**: loopback only (`127.0.0.1`). Real TLS or remote-host latency would shift absolute numbers; the relative picture for PK reads should hold but is not measured.
- **Sample size and noise**: four runs on a shared, loaded VM (load average 13). p99 values come from 200–5,000 samples and move 2–3× between runs, so only the medians should be used for comparison.
- **Lock entries**: none committed (per the sq-10 constraints). MT-03 must generate them.
- **Rollback under pg-mem**: the single rollback probe is conclusive for the ROLLBACK statement. I did not test savepoints or nested transactions.
- **Driver version currency**: versions are the latest I found on npm at run time; I did not check changelogs for breaking changes between `3.4.x` releases.
