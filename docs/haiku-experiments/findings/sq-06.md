# SQ-06: Force transaction conflicts against the Storage service

**Measurement date**: 2026-10-10 **Subject**: `platform/sqlite.ts` as built by item 15 (`Storage`,
`StorageLive`), on `origin/main` at `bccf85b`. **Script**: `work-scripts/deno/tx-conflict-stress.ts` (indexed
in `work-scripts/INDEX.md`).

## Question

When the same counter is written concurrently, or read in one mutation and written in another, does the writer
lose updates, reject them, or serialize them? Which code path decides?

"Convex commuter abstraction" is read here as: operations that **commute**, so applying them in any order
gives the same final state (for example, `+1` deltas), and so need no conflict detection at all. The verdict
below asks whether the platform needs a handler for that.

## Methodology

Real `StorageLive` over `node:sqlite` in a temp directory, one fresh database per round. Test doubles as in
`tests/unit/storage_test.ts`: `EventSink` collects into an array, `IdGen` counts, `Config` is `ConfigTest`.
The schema is one table, `counters(name, value)`, and the mutations are defined with `defineFunctions`.

- **A, concurrent increments.** 20 rounds × 50 fibers. Each fiber runs one mutation that reads the counter,
  yields once (`Effect.yieldNow`), then writes `value + 1`. Each round starts from a fresh database. Expected
  final value is 50 per round.
- **B, stale read across mutations.** Three sequential mutations, which is deterministic: M1 reads (value 0,
  version 1); M2 increments (value 1); M3 writes `M1.value + 1` = 1. Run three ways: plain M3; M3 guarded by
  M1's `_version` (the mechanism `makeMove` in `app/functions.ts` uses); and the guarded case followed by a
  re-read and retry. Expected final value after both increments is 2.
- **C, writes during backup.** 21 jobs forked at once: 10 increments, then `storage.snapshot()`, then 10 more
  increments. Checks that all 20 commit, that the snapshot opens and passes `PRAGMA quick_check`, and that its
  counter equals the number of increments committed before it in the queue.

Run: `deno run -A work-scripts/deno/tx-conflict-stress.ts` from the repo root, about 8 s. The `-A` is
required; see "Gotcha" below. Exit code is 1 if A loses an update or fails a mutation, or if C is not clean.
B's lost update is the expected observation, so it does not affect the exit code.

## What the code does

- **Writer queue.** `Semaphore(1)` is created at `platform/sqlite.ts:183` and entered with `withPermits(1)` at
  `:390`. `exclusive` (`:364-397`) admits at most `WRITER_QUEUE_CAP = 1000` jobs (`:99`, `:372`) and rejects
  the rest with `QueueFullError`. This is the only place writes are serialized.
- **Transaction.** `transaction` (`:290-361`) is `acquireUseRelease`: `BEGIN IMMEDIATE` at `:298`, `COMMIT` at
  `:311`, `ROLLBACK` in the release at `:326` when the commit did not run. `BEGIN IMMEDIATE` takes the write
  lock at the start, so a read-then-write cannot fail later with a lock-upgrade error. Within this process the
  semaphore is what prevents contention; `BEGIN IMMEDIATE` only makes the lock explicit.
- **Mutation.** `mutation` (`:502-526`) runs the handler inside `exclusive` and `transaction`. The `Documents`
  handle it passes in is expired when the transaction ends (`tx.active = false`, `:309` and `:322`) and
  checked before each statement (`live`, `:400-401`). A stale handle fails `ContextExpiredError`.
- **Snapshot.** `snapshot` (`:527-546`) goes through `exclusive` (`:528`), so it is queued with mutations.
  `VACUUM INTO` is at `:534`.
- **Versioning.** `_version` is bumped in SQL on every replace (`core/compile/write.ts:72`,
  `"_version" = "_version" + 1`). The platform does not compare it to anything. The only comparison is in the
  app: `makeMove` at `app/functions.ts:36` checks `game._version !== expectedVersion` and fails
  `ConflictError` (`:37`).
- **ConflictError in the storage layer.** `platform/sqlite.ts` never raises `ConflictError`. It appears only
  in `MUTATION_ERROR_TAGS` at `:137`, so the storage layer lets an app-raised `ConflictError` through as a
  typed failure. There is no read-set or write-set tracking, and no versioned commit check anywhere in the
  write path.
- **Serialization guarantee in the tests.** "Two competing moves cannot both commit"
  (`tests/core_test.ts:211`) holds because both moves send `expectedVersion: 1` and the app's version check
  rejects the second. The platform serializes them, but it is the client's version token that makes the second
  one fail.

## Gotcha: `VACUUM INTO` needs `-A` under `deno run`

With Deno 2.9.5, `node:sqlite` runs `VACUUM INTO` with the attached-database limit at 0, so every snapshot
fails with `StorageError: too many attached databases - max 0`. This happens for both bound and literal
destinations. It fails with `--allow-read --allow-write --allow-env`, and also with each of `--allow-net`,
`--allow-ffi`, `--allow-run`, `--allow-sys` and `--allow-import` added to those. It works with `-A`.
`deno test -A` works (`tests/core_test.ts` "standalone backup includes uncheckpointed WAL commits" passes),
and `deno task serve` / `deno task test` already use `-A`, so production snapshots and the test suite are not
affected. Only ad-hoc `deno run` with explicit grants is. The script's header documents this, and its first
run failed Scenario C for this reason before the cause was found.

## VERDICT

**HANDLER NOT NECESSARY for correctness.**

Mechanism: the single writer queue (`Semaphore(1)`, `platform/sqlite.ts:183`, `:390`) plus `BEGIN IMMEDIATE`
(`:298`) makes write-write lost updates impossible _inside_ a mutation. Measured: 1000 of 1000 concurrent
read-modify-write increments committed with zero loss, zero rollbacks and zero conflicts.

The one way a lost update happened is an application-level stale read across two mutations (scenario B plain).
The platform cannot see that read, and does not need to. The app already has the detection mechanism, the
`_version` guard that `makeMove` uses, and it works: scenario B guarded raised `ConflictError` and lost
nothing silently.

What a commutative-operation handler would add is not correctness. It would let clients send a `+1` without
reading first, so there would be no `expectedVersion` to get stale and no retry under contention. That is a
throughput and ergonomics feature. Scenario A already shows a `+1` can be done safely inside one mutation, so
it is not needed for correctness. Whether it is worth designing depends on a measurement this study did not
make: the retry rate of `expectedVersion` clients under real contention. If that rate is high, the commutative
handler is worth an Opus design; until then it is not necessary.

### Limits of this study

- Single process, single writer. The guarantee is in-process (the semaphore). A second process writing the
  same file would meet SQLite's write lock, and `busy_timeout=5000` (`:473`) would make it wait rather than
  conflict. This is from reading the code, not measured.
- The "B" scenario is deterministic (sequential awaits). A concurrent variant of the stale read would show the
  same result, since the stale read happens across transactions, but this was not run.
- Scenario A uses 50 fibers and 20 rounds on one droplet. The retry-rate question above needs a load test with
  real `expectedVersion` clients, which is out of scope here.
