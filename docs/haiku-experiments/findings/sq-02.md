# SQ-02: Baseline JSONL append throughput

**Measurement date**: 2026-10-10

**Disk context**: ext4 filesystem at /dev/vda1, 15% utilization, 137 GB available.

## Results

Baseline throughput for plain `Deno.FsFile` append-mode writes (no batching, one write per JSON-line record):

| Record size | Events/sec | MB/sec | Target floor      |
| ----------- | ---------- | ------ | ----------------- |
| 200 B       | 13,219     | 2.52   | ✓ +8,219 headroom |
| 1,024 B     | 7,616      | 7.44   | ✓ +2,616 headroom |
| 4,096 B     | 8,034      | 31.41  | ✓ +3,034 headroom |

(Median of 3 trials per size; see `docs/haiku-experiments/scratch/sq-02-append-bench.ts` for the script.)

## Interpretation

All three record sizes exceed item 11's acceptance bar of 5,000 events/sec (required to write 10,000 events in
under 2 seconds). The raw unbatched floor has substantial headroom: smallest headroom is +2,616 events/sec at
1 KB records, and largest is +8,219 events/sec at 200 B records.

**Conclusion**: item 11's batching design does _not_ need to buy throughput to clear the 2-second bar — all
three sizes are comfortably above the floor. The batching design's value is smooth backpressure and memory
efficiency, not raw speed.

Disk I/O is not the bottleneck on this droplet's ext4 filesystem for the record sizes tested. Item 11 can
focus on correctness and graceful shutdown semantics rather than optimizing past the measured floor.
