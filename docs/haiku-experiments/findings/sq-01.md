# SQ-01 Findings: Effect-TS Logger Batching & Backpressure Patterns

**Research date:** 2026-10-10  
**Target item:** Item 11 (Logger service, `Queue.dropping` + `forkScoped` consumer)

---

## Three Concrete Patterns

### Pattern 1: Time-Based Batching via `Stream.groupedWithin`
**Primitives:** `Stream.fromQueue()` → `Stream.groupedWithin(N, duration)` → `forkScoped` consumer

A stream reads from the log queue and flushes after *either* N records arrive OR duration expires. Effect 4.0.0+ optimized this (PR #8718) to start the timer only at first element, eliminating ~73K idle wakeups/sec.

**Tradeoffs:**
- ✓ Near-zero idle CPU overhead; natural backpressure (stream stalls if sink saturates)
- ✓ Predictable flush windows; good for network/file I/O amortization
- ✗ Batch sizes vary widely (1 to N); last batch may flush small if timeout expires first
- ✗ Latency jitter: a single log entry must wait up to `duration` before flush

**Fits item 11?** Moderately. Aligns with "flush when max(256 records, config.eventFlushMs)" but does not *force* the 256 threshold—a timeout might flush 50 records.

---

### Pattern 2: Size-Based Batching with Manual Threshold
**Primitives:** `Queue.dropping` + hand-rolled accumulator loop + condition check per entry

Maintain a buffer of log entries; on each offer to the queue, check: if buffer size ≥ 256, flush immediately; also flush on a timer (e.g., every `eventFlushMs`). This decouples the exact 256-record guarantee from any time-based slippage.

**Tradeoffs:**
- ✓ Hard size guarantee: flush always fires at ≥ 256 entries (no "wait for timeout")
- ✓ Time-based escape hatch prevents unbounded batches during idle periods
- ✓ Dropped entries can be counted *during* accumulation (simpler accounting)
- ✗ Must manage the accumulator buffer explicitly; higher code complexity
- ✗ Can spike CPU if checking size on every entry (mitigation: check every N entries)
- ✗ More stateful; harder to test (mutable buffer)

**Fits item 11?** Exactly. This is what item 11 explicitly specifies.

---

### Pattern 3: Lossy Queue Without Shutdown Semantics
**Primitives:** `Queue.dropping` alone, no finalizer, no consumer fiber

Queue only; dropped entries increment a counter; no guaranteed flush on exit.

**Tradeoffs:**
- ✓ Minimum code; absolute lowest latency
- ✗ **Event loss on peak load** (documented acceptable for non-critical metrics only)
- ✗ **No flush-on-shutdown:** buffered entries are abandoned if process exits
- ✗ No way to surface dropped-event count as a logged event (loss is silent)

**Fits item 11?** Not at all. Item 11 explicitly requires flush-on-shutdown and dropped-event logging.

---

## Recommendation

**Use Pattern 2 (Size-Based + Timer)** for item 11. Here's why:

Item 11's design is already explicit:
- `Queue.dropping(config.eventQueueCapacity)` — drop, don't block producers
- `forkScoped` consumer fiber — runs for the lifetime of the scope
- `max(256 records, config.eventFlushMs)` — hard size threshold, time-based escape hatch
- `Effect.addFinalizer` — drain remaining buffer before exit
- Dropped-event counts logged as `queue` events — loss is visible, not silent

Pattern 2 maps directly to this spec. Pattern 1 (groupedWithin) is *close* but does not guarantee the 256-record threshold; a timeout could flush after 50 entries, violating the "prefer batch size" rule.

**Key alignment points:**
- The size threshold (256) drives flush decisions; time (eventFlushMs) is the fallback
- Dropped-event accounting happens *in the accumulator loop*, not after-the-fact (simpler)
- `Effect.addFinalizer` on the scope ensures the last batch flushes before the file closes
- emit is `Effect<void, never>`: any sink failure (full disk, I/O error) increments the drop counter and writes to stderr once/minute; never propagates to handler

---

## Pitfalls to Avoid

1. **Finalizer ordering:** Finalizers run LIFO (last added, first executed). Ensure the log-flush finalizer runs *before* the file-close finalizer. Wrong order: file closes, then flush tries to write to a closed handle.
   - Mitigation: Add file-close finalizer first, flush second.

2. **Unbounded accumulator growth:** If time-based flush never fires (no entries for hours) and size threshold never hits (trickle of entries), buffer can grow indefinitely.
   - Mitigation: Always set eventFlushMs to a reasonable default (e.g., 5–10 sec), never `Infinity`.

3. **Blocking the producer:** Queue.dropping is *non-blocking*, so even with a full queue, offers succeed. But the *consumer loop* must not block producers. Never await the sink write inside the loop; always wrap it in a separate fiber or use a streaming operator.
   - Mitigation: Use `Stream` operators (groupedWithin, tap) or spawn the sink write in its own Effect.

4. **Signal handling bypass:** SIGTERM/SIGINT can abort the process before finalizers run if not handled carefully. The Effect runtime provides hooks; register signal handlers *before* starting the root fiber.
   - Mitigation: Use `Effect.runPromise` with proper signal handling; or use `ManagedRuntime` with `handleKill: false` to let your code handle signals.

5. **Accumulator overflow on burst:** A sudden burst of 10,000 entries in 1 ms will still force multiple flushes (one per 256), but the buffer will briefly grow large. Memory spikes are acceptable; data loss is not.
   - Mitigation: If memory is constrained, add a hard cap (e.g., 512 entries) and reject beyond that; drop and log.

## Implementation Sketch (Effect pseudocode)

```typescript
// Consumer fiber
const consumer = (queue, config) =>
  Effect.gen(function* () {
    let buffer = [];
    const tick = yield* Clock.periodic(config.eventFlushMs);
    
    while (true) {
      // Receive next entry OR timeout
      const entry = yield* Queue.take(queue).pipe(
        Effect.race(tick)  // timeout triggers flush
      );
      
      buffer.push(entry);
      
      if (buffer.length >= 256) {
        yield* writeToSink(buffer, config);
        buffer = [];
      }
    }
  });

// Shutdown
const program = Effect.gen(function* () {
  const scope = yield* Scope.make();
  
  yield* Scope.addFinalizer(scope, 
    // Flush remaining buffer
    Effect.sync(() => {
      if (buffer.length > 0) {
        writeToSinkSync(buffer, config);
      }
    })
  );
  
  yield* Scope.addFinalizer(scope,
    // Close file handle
    Effect.sync(() => handle.closeSync())
  );
  
  yield* Fiber.forkScoped(consumer(queue, config), { scope });
  yield* yourProgram;
});
```
