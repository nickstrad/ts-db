## Summary

- Harness: `work-scripts/bash/k6-baseline.sh <run-id-prefix>` runs `perf:smoke` three times, each against a
  fresh server, and extracts the numbers from each `summary.json` with python3.
- Final measured baseline (prefix `sq08-baseline-v2`): all 3 runs exit 0, all thresholds pass, 0 failed
  requests of 544, 0 failed checks of 1088. p95 ranges 66.27–105.09 ms; p99 ranges 98.92–225.68 ms.
- Recommended for item 25: `http_req_duration p(95)<160`. Keep `http_req_failed rate<0.01` and
  `checks rate==1.0`. **No p(99) row**: p99 spread across runs is 71%, above the 25% stability rule.
- Caveat that matters most: the two invocations of the harness differed a lot (p95 mean 51.84 ms vs 85.43 ms),
  and the host was under heavy load from other sessions. The 160 ms limit is anchored to this loaded host and
  should be re-checked on a quiet host before it is treated as a stable gate.
- Quiet-host re-check (Opus 5.5 review, 2026-10-11, prefix `revcheck`, load 0.44–1.28 throughout): p95
  31.56–37.02 ms, p99 57.55–100.14 ms, p50 mean 15.75 ms, ~6.9 req/s, 0 failures in 632 requests. Under the
  same 1.5x rule that anchors `p(95)<60` on a quiet host. **Decide the gate host before the number**: `<60`
  would have failed every loaded-host run; `<160` is ~4.3x the quiet-host worst p95. Host contention moves p95
  2–3x — more than any regression the gate is meant to catch.

### How the harness extracts numbers

- Reads `logs/k6/<run-id>/summary.json` for each run with python3 (`python3 -I`). A missing summary is a hard
  error (exit 1). It does not abort on k6 non-zero exits, which are recorded as data.
- Fields: `http_req_duration` `med` (p50), `p(95)`, `p(99)`, `avg`; `http_reqs` count and rate (req/s);
  `http_req_failed` rate; `checks` passes and fails; `iterations` count; each threshold's `ok` flag.
- Refuses to start if `logs/k6/<prefix>-rN` or `logs/k6/<prefix>` already exists, so a stale `summary.json`
  cannot stand in for a fresh run.
- Writes `logs/k6/<prefix>/baseline.json` with raw per-run values, aggregates, the rule constants, and the
  recommended thresholds.
- On adoption (2026-10-11): each run also records the host's 1/5/15-minute load averages
  (`logs/k6/<run-id>/load_avg`, and per run inside `baseline.json`); the harness warns on stderr when a run's
  1-minute load exceeds the CPU count.

### Threshold rules (fixed before the measured run)

- `p(95)` limit = worst observed p95 across the runs x 1.5, rounded up to 10 ms. The 1.5x headroom is a
  convention (a common rule of thumb fixed ahead of time), not a figure derived from the observed variance.
- `p(99)` row only if (max - min) / mean of p99 across runs is at most 25%.
- `http_req_failed` and `checks` rows are kept as they are unless the data says otherwise.

### Bug found in the first invocation (fixed)

The first invocation (`sq08-baseline`) read `http_req_failed` `fails` as the failed count. In k6's Rate
metric, `passes` counts the true observations (failed requests) and `fails` counts the rest. Its summary
showed the inversion:

```
$ python3 -I -c "... logs/k6/sq08-baseline-r1/summary.json ..."
summary http_req_failed values: {'rate': 0, 'passes': 0, 'fails': 200}
summary http_reqs values: {'count': 200, 'rate': 6.476464360094959}
raw.json http_req_failed points: 200 with value 1 (failed): 0
```

So the first invocation's failed-count column showed "592 failed of 592 requests". The rate column (0) was
correct. The fix reads `passes`. The latency, throughput and checks columns of the first invocation were not
affected.

### Cross-check of k6's percentiles (one run)

k6's summary percentiles are estimates. Nearest-rank values computed from the raw points of
`sq08-baseline-v2-r3`:

```
$ python3 -I -c "..."   # nearest-rank over http_req_duration points in logs/k6/sq08-baseline-v2-r3/raw.json
n raw points 176
nearest-rank from raw.json: p50 40.62 p95 114.01 p99 232.54
k6 summary values:          med 40.62 p95 105.09 p99 225.68
```

p50 agrees exactly. p95 is about 8% lower in k6's summary than nearest-rank, and p99 about 3% lower. The
threshold is evaluated by k6 against its own estimate, so the anchor uses k6's value. Anchoring on
nearest-rank p95 (114.01 ms) would give a 180 ms limit under the same rule.

## Recommended threshold table for item 25

Rule: limit = worst observed p95 x 1.5 (convention, not derived), rounded up to 10 ms. Worst p95 across all
six runs (both invocations) is 105.09 ms, the same value as the final invocation alone, so the limit is the
same either way.

| threshold                          | measured anchor and justification                                                                                                                                                                             |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `http_req_duration p(95)<160`      | worst p95 105.09 ms over the 3 final runs (mean 85.43 ms, range 66.27–105.09); x1.5 headroom (convention) rounded up to 10 ms. Current limit is p(95)<250. Anchored on a loaded host (load 12.88 on 4 vCPUs). |
| `http_req_failed rate<0.01` (keep) | 0 failed of 544 requests across the 3 final runs (0 of 592 in the first invocation). The current limit is kept.                                                                                               |
| `checks rate==1.0` (keep)          | 0 failed of 1088 checks across the 3 final runs. The current rule is kept.                                                                                                                                    |
| p(99) (not recommended)            | Spread across the 3 final runs is 71% (98.92 to 225.68 ms), above the 25% rule. With ~181 requests per run, p99 is the value of about 2 samples. No stable value.                                             |

The three existing thresholds stay in `perf/smoke.js`. Item 25 can tighten p95 to `<160` if it accepts the
flakiness risk described under Honest limits. On a quiet host the same rule anchors `p(95)<60`.

## Not covered

- **Multi-process runs.** Only the single-process `deno task serve` was run, one VU at a time.
- **Backup and restore under load.** Not run.
- **Sustained soak beyond 30 s.** The smoke scenario is 30 s; nothing longer was run.
- **The k6-vs-platform join assertion** (item 25's own acceptance work): not done. No `raw.json` was ingested
  into DuckDB, and no server-side event durations were compared with the k6 trace ids.
- **Production capacity claims.** None are made. The numbers are for one loopback server on this VM under load
  from other sessions.
- **Load shapes.** The lx-04 ramp, spike and sustained shapes were not rerun. Their findings were read only.

## Honest limits

- **Host contention.** The VM is shared. `uptime` at 13:07 showed a 1-minute load average of 12.88 on 4 vCPUs,
  so other sessions were likely loading the host during the final invocation. The two invocations differ
  markedly: p95 mean 51.84 ms in the first and 85.43 ms in the final. Neither set was taken on a quiet host by
  me; the review's quiet-host re-check (above) closes that gap. On adoption the harness records per-run load
  in `baseline.json` and warns above the CPU count.
- **Sample size.** Each run has 176–200 requests (22–25 iterations of 8 requests). p95 is about the 9th to
  10th slowest request. p99 is about the 2nd slowest. That is why no p99 row is recommended.
- **req/s is not throughput.** `perf/smoke.js` ends each 8-request iteration with `sleep(1)`, so the ~5.6–6.9
  req/s figure mostly reflects that think time plus iteration latency; it moves only when iteration latency
  moves. It is a sanity column, not capacity data.
- **Accidental runs (not in any table).** Two mistakes produced extra scenario runs before the baseline: the
  harness was run with prefix `logs` (three runs: `logs-r1..r3`, `logs` dir), and once from `/tmp` with prefix
  `sq08-precheck-x` where the pipe to `head -1` killed the harness after run 1 (`sq08-precheck-x-r1`). These
  run dirs were deleted and their numbers are not used anywhere in this document.
- **Not executed: the failure paths of the harness.** Not executed: the refuse-existing-prefix guard, the
  missing-`summary.json` error, and a harness run with a failing k6 threshold (so the "k6 exit != 0 is data"
  path was not exercised). The `thresholds failing` column was only seen as `none`.
- `perf/smoke.js`, `perf/`, `deno.json`, `core/`, `platform/`, `sdk/`, `app/`, `tests/`, `scripts/` were not
  modified.
