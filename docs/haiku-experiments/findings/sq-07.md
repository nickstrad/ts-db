# SQ-07: DuckDB segfault reproduction and triage

**Question:** Can the intermittent exit-139 (SIGSEGV) seen in ts-db test runs be reproduced on demand, and
where does it live: `duckdb.node` native code, the Deno FFI boundary, or the test harness?

**Measurement date:** 2026-10-11. **Tree:** `haiku/sq-07` at `e423ed1` (the `main` base; no plan-item code).
**Host:** 4 vCPU, 8 GB RAM, kernel 6.8.0-139-generic. Deno 2.9.5. The VM was shared and loaded during the runs
(load average 12.5 on 4 cores at the first crash, from other sessions' `deno task test`, `perf:mixed`,
`serve`, and a reader process). Core dumps are off (`ulimit -c` = 0, `core_pattern` = apport); `gdb` and
`coredumpctl` are not installed, so **no native stack was captured**.

Lead sources, treated as leads: lx-01 reported exit 139 on seeds 14, 96, 179, 187, 199 under
`deno task test:prop` (`git show origin/luna/lx-01-seed-sweep:docs/luna-experiments/findings/lx-01.md`). Item
37's commit `f581e8e` records two exit-139 runs of single-process `deno task test` in "the DuckDB native
worker", and says the flake reproduces on clean main (that claim is not verified here).

not a test assertion.

## Crash signatures (all three 139s)

The two single-file crashes printed every test's `ok` line and then ended with no summary line, which means
the process died after the last test finished. Seed 199 (`run-1.log`) shows five `ok` lines with
`offsets_test.ts`'s five tests and no `passed |` line. The default-seed crash (`run-2.log`) shows the same.
The passing reference run ends with `ok | 5 passed | 0 failed (1m19s)`. The `deno task test` crash (run 3, 319
`ok` lines, no summary line) is **not** shown to be in teardown: it may be mid-run in a later file. Only the
two single-file crashes are established as teardown.

`dmesg` immediately after each crash (verbatim):

```
[2380989.995602] tokio-runtime-w[3286151]: segfault at 70fe0bcda09e ip 000070fe0bcda09e sp 000070f9259f5348 error 14 likely on CPU 0 (core 0, socket 0)
[2381265.952926] tokio-runtime-w[3316274]: segfault at 1 ip 0000000000000001 sp 00007a4be7bf8348 error 14 likely on CPU 2 (core 2, socket 0)
[2381845.544325] tokio-runtime-w[3365715]: segfault at 77aaaaaa9764 ip 000077aaaaaa9764 sp 000077ade6bf0348 error 14 likely on CPU 1 (core 1, socket 0)
```

The first two belong to the seed-199 and default-seed `offsets_test.ts` crashes (`run-1.dmesg`,
`run-2.dmesg`); the third is the `deno task test` run 3 crash (`c4-task-test/run-3.dmesg`). A fourth line,
`[2381913.673401] tokio-runtime-w[3374578]:
segfault at 7d67b0fe1af0 ip 00007d67b0fe1af0 ... error 15`,
appeared 68 s after the third, with no matching exit 139 in my chains. It is **unattributed**: it may belong
to another session's deno process, and I did not prove otherwise.

No OOM kill appears in `dmesg` during my runs. The only `Out of memory: Killed process` lines are from before
the runs (timestamp `2353491`, pid 2812049, deno), so **OOM is ruled out for these three crashes**.

## Fault-location verdict

**Unknown native code, located in Deno's own runtime thread. Not established as DuckDB, the FFI bridge, or the
harness.**

Evidence for the location:

- The faulting thread is named `tokio-runtime-w`. Listing threads of a live `deno test` process showed three
  `tokio-runtime-w` threads (`/proc/<pid>/task/*/comm`), so that name is Deno's Rust runtime, not a DuckDB
  thread. I did **not** check the thread names that DuckDB creates, so I cannot say DuckDB threads never take
  that name.
- The instruction pointer equals the fault address (`ip 70fe0bcda09e` / `ip 77aaaaaa9764`), or is `1`, or
  `0x20` in earlier lines: a jump to a non-code address (corrupted or null function pointer). That is the
  signature of a wild call through a bad pointer, not a fault inside a normal function. It is the same pattern
  as earlier `tokio-runtime-w` faults on this VM (`2373842`, `2374043`, `2376811`, `2376967`, `2377444`,
  `2378731`, `2378812`), which predate my runs and include processes I did not start.

Evidence against the test harness: the JS test code ran to completion (every `ok` printed) before two of the
three crashes. Evidence against a seed-specific or parallel-only cause: the default seed crashed, and `-j 2`
ran 10 clean.

Ruled out:

- OOM kill (no OOM lines in the window; crashes are 139, not 137).
- Parallelism alone (0/10 at `-j 2`, 0/10 for `eventlog_test.ts`).
- A single seed (default seed crashed; seeds 14, 96, 179, 187 passed on one run each).

Not ruled out: a native stack is needed to name the library.

## Recommended next step

**Chase, do not quarantine yet.** The rate is low (about 1 in 18 for `offsets_test.ts`, 1 in 5 for
`deno task test`), but it is real and reproducible on demand by repetition. Quarantine would hide a
wild-pointer crash in the runtime. The next step that would settle the location:

1. Run the single-file loop with core dumps enabled, `ulimit -c unlimited` and a writable `core_pattern`, on
   an idle VM (one deno process at a time), until a core lands. Install `gdb` and read the faulting thread's
   stack. A stack through `libduckdb`/`@duckdb/node-api` settles DuckDB; a stack entirely in `libdeno`/`deno`
   settles the runtime.
2. Check which native modules `offsets_test.ts` loads (`deno info tests/property/offsets_test.ts` on the
   import graph), to see whether `@duckdb/node-api` is the only native addon in the process. Fewer candidates
   make the core stack easier to read.
3. Confirm item 37's "reproduces on clean main" claim with the same loop on `main`: this tree is `e423ed1`,
   which is the base item 37 cites, so the 3/53 result above already covers it, but the report should say so
   explicitly.

Until (1) lands, track the rate with `work-scripts/bash/sq-07-segfault-stress.sh`.
