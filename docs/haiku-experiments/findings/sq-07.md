# SQ-07: DuckDB segfault reproduction and triage

**Question:** Can the intermittent exit-139 (SIGSEGV) seen in ts-db test runs be reproduced on demand, and
where does it live: `duckdb.node` native code, the Deno FFI boundary, or the test harness?

**Measurement date:** 2026-10-11. **Tree:** `haiku/sq-07` at `e423ed1` (the `main` base; no plan-item code).
**Host:** 4 vCPU, 8 GB RAM, kernel 6.8.0-139-generic. Deno 2.9.5. The VM was shared and loaded during the runs
(load average 12.5 on 4 cores at the first crash, from other sessions' `deno task test`, `perf:mixed`,
`serve`, and a reader process). Core dumps are off (`ulimit -c` = 0, `core_pattern` = apport); `gdb` and
`coredumpctl` are not installed, so **no native stack was captured**.

**Adopted 2026-10-11** as `work-scripts/bash/segfault-stress.sh` plus this findings doc, with corrections from
the Opus 5.5 review applied below: the dmesg attribution (crash 3's line was another process's), the
fault-location headline ("not DuckDB" does not follow), the parallelism claim, the seed-14 framing (coverage
guard, not invariant failure), and the item-37 paraphrase.

Lead sources, treated as leads: lx-01 reported exit 139 on seeds 14, 96, 179, 187, 199 under
`deno task test:prop` (`git show origin/luna/lx-01-seed-sweep:docs/luna-experiments/findings/lx-01.md`). Item
37's commit `f581e8e` records "deno task ci passed (539 unit + 71 prop, 0 failed) after two exit-139
duckdb.worker flakes" — it says nothing about single-process `deno task test` and makes no "clean main" claim.

## Repro result

**Reproduced.** 3 exit-139 crashes in 53 runs across the matrix below. Each is an isolated process segfault,
not a test assertion.

`work-scripts/bash/segfault-stress.sh`):

Crash rate: 2/35 on `offsets_test.ts` alone (about 1 in 18); 0/10 on `eventlog_test.ts`; 1/5 on the full
`deno task test`; 0/2 on `deno task test:prop` with seed 199.

Seed 14 on `deno task test:prop` did **not** reproduce lx-01's exit 139. It failed an assertion instead:

```
retention follows committed ingest: exactly once, nothing un-ingested lost, across crash interleavings [seed=14] ... FAILED (21s)
error: AssertionError: no late append was ever blocked by its stale watermark
FAILED | 70 passed | 1 failed (2m4s)
```

So seed 14 is a **coverage (vacuity) guard failure, not an invariant failure**: all 20 generated cases
satisfied the property, but none of them reached the `unread-tail` blocked path (`"blocked":{}`), so the guard
at `retention_ingest_test.ts:573` fails. That is test-tuning work for the item-36 owner (raise `CASES`, raise
the late-append op weight, or add a deterministic `unread-tail` anchor) — not a retention bug, and not part of
the segfault.

## Crash signatures (all three 139s)

The two single-file crashes printed every test's `ok` line and then ended with no summary line, which means
the process died after the last test finished. Seed 199 (`run-1.log`) shows five `ok` lines with
`offsets_test.ts`'s five tests and no `passed |` line. The default-seed crash (`run-2.log`) shows the same.
The passing reference run ends with `ok | 5 passed | 0 failed (1m19s)`. The `deno task test` crash (run 3, 319
`ok` lines, no summary line) is **not** shown to be in teardown: it may be mid-run in a later file. Only the
two single-file crashes are established as teardown.

`dmesg` after the two single-file crashes (attribution confirmed by pid/tid and timestamp, after correcting
for the kernel clock running ~197 s behind wall time):

```
[2380989.995602] tokio-runtime-w[3286151]: segfault at 70fe0bcda09e ip 000070fe0bcda09e sp 000070f9259f5348 error 14 likely on CPU 0 (core 0, socket 0)
[2381265.952926] tokio-runtime-w[3316274]: segfault at 1 ip 0000000000000001 sp 00007a4be7bf8348 error 14 likely on CPU 2 (core 2, socket 0)
```

**The `deno task test` run-3 crash has no kernel record.** The line originally attributed to it
(`[2381845…] ip 000077aaaaaa9764`) predates the whole chain by about 10 minutes and belongs to another
process's crash, as does the "unattributed" `[2381913…]` line. The attribution was timing-based; the adopted
script now records each child's pid and greps `dmesg` for that pid's thread ids instead.

No OOM kill appears in `dmesg` during my runs. The only `Out of memory: Killed process` lines are from before
the runs (timestamp `2353491`, pid 2812049, deno), so **OOM is ruled out for these three crashes**.

## Fault-location verdict

**Unknown native code, on a Deno tokio blocking-pool thread created at startup. "Not DuckDB" does NOT
follow.**

Evidence for the location:

- The faulting thread is named `tokio-runtime-w`, but the `comm` name **cannot** separate Deno from DuckDB:
  creating a `DuckDBInstance` adds three threads also named `tokio-runtime-w` (Linux threads inherit `comm`
  from their creator), so the name is not Deno's alone. Thread listing of the live process that later crashed
  showed the faulting tid as pid+8, created before `deno-test-watch` — a Deno startup tokio (blocking-pool)
  thread, not a DuckDB worker. Blocking-pool threads still run arbitrary offloaded work, which may include
  N-API async work or finalizers, so "not DuckDB" does not follow.
- The instruction pointer equals the fault address (`ip 70fe0bcda09e`), or is `1`: a jump to a non-code
  address (corrupted or null function pointer). That is the signature of a wild call through a bad pointer,
  not a fault inside a normal function. It is the same pattern as earlier `tokio-runtime-w` faults on this VM,
  which predate my runs and include processes I did not start. Extra signal: every `tokio-runtime-w` segfault
  in `dmesg` (~25 since uptime 2354140) has `sp …348` (the same page offset) — one call site at a fixed stack
  depth, i.e. a single bug.
- The crashing process has DuckDB mapped (`/proc/<pid>/maps` lists `duckdb.node` and `libduckdb.so`).

Evidence against the test harness: the JS test code ran to completion (every `ok` printed) before two of the
three crashes. Evidence against a seed-specific cause: the default seed crashed. (10 clean runs at `-j 2` is
statistically empty at a ~6% rate, and the "sequential" chains overlapped each other, so it proves nothing
about parallelism.)

Ruled out:

- OOM kill (no OOM lines in the window; crashes are 139, not 137).
- A single seed (default seed crashed; seeds 14, 96, 179, 187 passed on one run each).

Not required: parallelism — crashes occur at `-j 1`.

Not ruled out: a native stack is needed to name the library.

## Recommended next step

**Chase, do not quarantine.** The rate is low (about 1 in 18 for `offsets_test.ts`, 1 in 5 for
`deno task test`), but it is real and reproducible on demand by repetition, and it also fires mid-suite in
`deno task test`. Quarantining `offsets_test.ts` would not remove it. Quarantine would hide a wild-pointer
crash in the runtime. The cheapest discriminating next experiments:

1. Rerun the stress loop with DuckDB pinned to one thread (`threads=1` in the instance config used by the test
   helpers), and make teardown explicitly close connection then instance and await all pending queries before
   the test ends. A rate drop to 0/40+ implicates DuckDB worker or finalizer teardown.
2. Use the pid-fixed script (`work-scripts/bash/segfault-stress.sh`, adopted 2026-10-11) so dmesg attribution
   is by thread id, not timing.
3. Cores: `ulimit -c unlimited` with a file `core_pattern` (coordinate on the shared VM — currently the apport
   pipe), then `gdb` on the faulting thread.

Working hypothesis (not a finding): use-after-free of a native callback/vtable at DuckDB finalization on a
blocking-pool thread. The teardown timing, the wild IP, and a blocking-pool thread together fit it.

Until a core lands, track the rate with `work-scripts/bash/segfault-stress.sh`.

## Limitations and not executed

- Not executed: a native stack (no core dumps, no `gdb`); a DuckDB-only minimal script without the harness; a
  run with an idle VM (the VM had other sessions' deno processes throughout).
- Not executed: `deno task ci`, `deno task integration`, and the other seeds from lx-01 (`179`, `187` on
  `deno task test:prop`).
- The full-suite `deno task test:prop` ran with seeds 199 (×2) and 14 (×1) only.
- The adopted script's dmesg attribution (pid + thread-id grep) postdates these runs; the runs above
  attributed by timing only, and one attribution was wrong (see Crash signatures).
- The "sequential" chains overlapped each other (chain1+chain2 both started 13:01, chain3+chain4 both 13:32),
  so they were not isolated runs.
- The `/proc/<pid>/task/*/comm` thread listing was never repeated after DuckDB opened; DuckDB is confirmed
  mapped into the crashing process via `/proc/<pid>/maps` instead.
- The sq-07 entry was missing from the board table in `docs/haiku-experiments.md` (only sq-01 to sq-06
  appeared). Added on adoption (2026-10-11).
