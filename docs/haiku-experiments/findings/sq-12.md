# SQ-12: item-23 query executability harness

**Measurement date**: 2026-10-11 (`haiku/sq-12`, based on `origin/main` e423ed1).

**Adopted 2026-10-11** as `work-scripts/deno/query-executability.ts` (durable name), with corrections from the
Opus 5.5 review applied below: the `--schema lx02` reproduction mode was dropped on adoption; the punch list
is 7 queries (k6-vs-platform also has `kind` drift, hidden behind the `date_bin` error); the trace-timeline
fix needs only the `tags` cast (`path` is already `VARCHAR`); a PASS with 0 rows still counts as a pass (PASS
proves bind+run, not "returns rows"); and the "plan §4.3 catalog" queries are lx-02's drafts, not plan SQL.
The `--schema` arg-parsing nit was also fixed (a stray first argument is no longer treated as a schema name).

**Harness**: `work-scripts/deno/query-executability.ts` (on the quest branch:
`work-scripts/deno/sq-12-query-executability.ts` with an additional `--schema lx02` mode, dropped on
adoption).

**Run command**: `deno run -A work-scripts/deno/query-executability.ts` from the repo root.

## Method

- **What it does**: creates the event-log tables in an in-memory DuckDB (1 thread, 1 GB limit), inserts 300
  deterministic rows into each of the 8 event tables, then runs all 18 queries (8 starter + 10 catalog drafts)
  and prints `PASS`/`FAIL` per query. A failure prints the first line of the DuckDB error. The script exits 0
  only if all 18 pass. **A PASS proves the query binds and runs; it does not prove the query returns rows** —
  a PASS with 0 rows happens (see k6-vs-platform below).
- **Schema**: the DDL from `core/eventlog/ddl.ts` (`EVENTLOG_DDL`), the current v2 schema.
- **Seed**: `0x5912` (mulberry32). Generators emit every column of each table; a column with no generated
  value throws instead of inserting NULL.
- **Row counts**: 300 per table (2,400 total), plus a 300-line JSONL file for `log-level-distribution`.
- **SQL source**: the 8 starter queries are `scripts/duckdb/*.sql` with comment headers removed. The 10
  catalog-draft queries are lx-02's drafts, copied from
  `origin/luna/lx-02-query-bench:work-scripts/deno/lx-02-query-bench.ts` — lx-02's interpretations of plan
  §4.3's name/question table, which has no SQL. Both are embedded in the script. Every non-comment line of the
  starter files, and every SQL line of lx-02's catalog drafts, is present in the script (checked with
  `grep -F`).
- **DuckDB version** (from the script's own `SELECT version()`):

```
duckdb v1.5.6; schema item21; seed 0x5912; 300 rows/table
```

- **Tooling checks** (all run on the final file):

```

$ deno lint work-scripts/deno/query-executability.ts
```

(`deno lint` first reported one unused import; it was removed and the second lint run is clean.)

## Determinism

The adopted single-schema mode was run twice; the stdout of the two runs was compared with `diff`:

```
run1 exit=1
run2 exit=1
runs 1 and 2 IDENTICAL
```

The output has no timings, paths or random values. (On the quest branch each schema mode was run twice with
the same result; the default invocation matched `--schema item21` byte-for-byte.)

## Reproduction of the two known lx-02 failures

Both reproduce under the dropped `--schema lx02` mode, with the error signatures lx-02 documented:

| Failure                      | lx-02 documented (`docs/luna-experiments/findings/lx-02.md`)               | Harness, `--schema lx02`                                                                                                            |
| ---------------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `starter:trace-timeline.sql` | `Malformed JSON ... Input: "/api/7" when casting from source column extra` | `Conversion Error: Malformed JSON at byte 0 of input: unexpected character.  Input: "/api/7" when casting from source column extra` |
| `catalog:k6-vs-platform`     | fails because the pinned DuckDB build has no `date_bin` scalar function    | `Catalog Error: Scalar Function with name date_bin does not exist!`                                                                 |

Caveat on the first row: lx-02's findings abbreviate the middle of the message with `...`. The part it quotes
(`Malformed JSON`, `Input: "/api/7"`, `when casting from source column extra`) matches exactly. I cannot
confirm the elided part is identical, because the lx-02 run's raw output is not in the repo. The `date_bin`
signature is quoted in full by lx-02's prose and matches.

### Why the trace-timeline failure is masked under the current schema

Under the current v2 schema, the same query fails with `Referenced column "kind" not found`. v2 renamed
`platform_events.kind` to `event_kind` and `http_events.kind` to `handler_kind`. The run reports only the
missing-column error, so the JSON UNION conflict is not reached in the harness output. (I did not check
DuckDB's binder internals; the probe below shows what happens once the renames are made.)

To check that the JSON bug would still occur once that rename is handled, I ran a throwaway probe in `/tmp`
(not in the repo). It used the v2 DDL, one row per table with `trace-7`, and the verbatim
`scripts/duckdb/trace-timeline.sql` with only the two `kind` references changed (`event_kind AS kind` in the
platform arm, `handler_kind AS kind` in the http arm):

```
$ deno run -A --config deno.json /tmp/sq12-probe/probe.ts
renamed: true
FAIL Conversion Error: Malformed JSON at byte 0 of input: unexpected character.  Input: "/api/7" when casting from source column extra
```

So the JSON UNION bug is present in the v2 schema too. It is only hidden in the harness's default run.

## Verdict

**Does the harness satisfy the per-query execution check lx-02 recommended?** For the mechanism, yes. It runs
every query against the item-21/35 tables and reports the error for each one. It has a deterministic seed and
a non-zero exit on failure, and it reproduces both lx-02 failures with their documented signatures (under the
dropped `lx02` mode). For the gate, not yet: against the current DDL, the check fails 7 of 18 queries, so it
cannot pass until the SQL is fixed.

Verified results:

- Current DDL: 11/18 pass. Seven queries use `kind` (renamed to `event_kind`/`handler_kind` in v2), and one of
  them (`k6-vs-platform`) additionally uses `date_bin` — DuckDB reports the `date_bin` error first, which
  hides its `kind` drift.
- Known failures reproduce under the lx-02 schema: `trace-timeline` (JSON UNION) and `k6-vs-platform`
  (`date_bin`).
- Re-running gives identical output.

**Not executed**: I did not run any query against real ingested data or the ingest pipeline. I did not check
the timing or plan behaviour of any query, and I did not test whether `time_bucket` (lx-02's suggested
replacement) produces the same bucket semantics as `date_bin`.

### What item 23 would need to change to adopt this

1. **Fix the v1→v2 column drift** in every query that uses `kind` — 7 queries, not 6: `recent-errors`,
   `event-counts-by-type`, `error-rate-by-handler`, `handler-throughput`, `trace`, `trace-timeline`, **and
   `k6-vs-platform`** (its `p` CTE has `WHERE kind = 'handler'`; the `date_bin` error hides this until it is
   fixed). In `platform_events` that means `event_kind` (the record kind) or `handler_kind` for handler
   events, depending on what the query means. In `http_events` it means `handler_kind`. The plan should decide
   which one each query means before anyone edits the SQL. `scripts/duckdb/event-counts-by-type.sql` already
   notes that the `kind` overload is unresolved.
2. **Fix the `trace-timeline` UNION** by casting the JSON `tags` to `VARCHAR` (as the `catalog:trace` query
   already does with `CAST(tags AS VARCHAR)`), so the `extra` column has one deliberate type. Casting `path`
   is redundant — `http_events.path` is already `VARCHAR`. This is a fix sketch; it is not applied anywhere.
3. **Replace `date_bin`** with a function the pinned DuckDB (v1.5.6) has. lx-02 suggested `time_bucket`. Not
   executed here, so the bucket semantics (origin, alignment) are unverified.
4. **Point the harness at the real catalog** once item 23 lands: replace the embedded query texts with the
   `platform/analysis/catalog.ts` entries and keep the schema, seed and PASS/FAIL logic. The `lx02` mode was
   dropped on adoption, since it existed only to reproduce a historical schema.
5. **Keep the harness as the item-23 gate**: run it in `ci` (or as a `deno task`) so a catalog change that
   breaks execution fails before release. **Caveat:** the harness proves queries bind and run, not that they
   return rows — with all fixes applied, `catalog:k6-vs-platform` passes with 0 rows (the synthetic timestamps
   are spread at random over 30 days, so the 10-second bucket join almost never matches). Item 23's acceptance
   criteria require "return rows", so item 23 needs a non-zero-row check or seeded data guaranteeing bucket
   overlap (e.g. k6 and handler events in the same 10-second buckets).

None of these fix sketches were applied to `core/`, `platform/`, `scripts/duckdb/`, `tests/`, or any plan
file.
