# sq-09: Better Auth headless feasibility pre-spike (MT-08 go/no-go gate)

**Model**: claude-haiku-5-5 (Haiku 5.5). **Date**: 2026-10-11.

**Adopted 2026-10-11** with corrections from the Opus 5.5 review: the "unfiltered" paste label was fixed (the
step-6 block was trimmed), the stale cleanup line was removed (the container is gone), the misframed
SQLite-storage recommendation was dropped (MT-08 targets Postgres per the plan), and the plan-spec departure
is now noted (raw `fetch` + cookie was used, not `createAuthClient` + token as MT-08 step 1 specifies). The
review also re-ran both variants on a fresh DB and closed the open items below.

**Question**: Can better-auth run under Deno — import the package, mount the handler, and complete a headless
sign-up/sign-in round trip against a scratch Postgres, capturing a session token and using it to authenticate
a request? Yes or no, with evidence.

**Verdict: GO.** Both the import-map form and the inline-pinned `npm:` form (the form the multitenancy plan
requires for MT-08) pass the full round trip. Every claim below is backed by the command output pasted under
it. Nothing in the verdict is labeled "pass" without a run behind it.

**Methodology**: All experimental code lives in `/tmp/auth-spike/` (throwaway). The only repo file written is
this one. Single runs per configuration (n=1 per variant), plus one rerun of the first variant to check
idempotency. The scratch database is `auth_spike_test`; no other database was read or written.

**Spec departure (noted on adoption):** MT-08 step 1 specifies the vanilla `createAuthClient`
(`better-auth/client`) to capture a token and call a tenant endpoint with it. This spike used raw `fetch` and
authenticated with the **cookie**; the body `token` was printed but never exercised as an
`Authorization: Bearer` credential. The Opus 5.5 review probed this separately: without `plugins: [bearer()]`
the body token returns 401; with the plugin it returns 200 — so MT-08 must decide the bearer-vs-cookie token
transport before build (fed into the MT-08 brief).

### Step 3: The spike (`/tmp/auth-spike/spike.ts`, import-map variant)

Core config (the minimal recipe):

```ts
import { betterAuth } from "better-auth";
import { getMigrations } from "better-auth/db/migration";
import { Kysely, PostgresDialect } from "kysely";
import pg from "pg";

const db = new Kysely<any>({
  dialect: new PostgresDialect({ pool: new pg.Pool({ connectionString: DATABASE_URL, max: 4 }) }),
});
const auth = betterAuth({
  baseURL: BASE_URL, // http://127.0.0.1:<port>
  basePath: "/api/auth",
secret: <redacted>
  trustedOrigins: [BASE_URL],
  database: { db, type: "postgres" },
  emailAndPassword: { enabled: true, autoSignIn: false },
});
const { toBeCreated, toBeAdded, runMigrations } = await getMigrations(auth.options);
await runMigrations();
// Deno.serve: if url starts with /api/auth/ → return auth.handler(req)
// scratch endpoint /api/whoami → auth.api.getSession({ headers: req.headers })
```

## Verdict

**GO.** better-auth 1.7.7 runs under Deno 2.9.5. It imports, the handler mounts on `Deno.serve` at
`127.0.0.1`, and a headless email/password sign-up and sign-in complete against a scratch Postgres 17.11. The
sign-in response carries a session token in both the `set-cookie` header (`better-auth.session_token`) and the
JSON body (`token`). The captured cookie authenticates `/api/whoami` (200 with the user's email), and the same
endpoint without the cookie returns 401. This was verified in the import-map variant and the inline-pinned
variant, and across two runs against the same database.

**Minimal working recipe**:

1. Imports: `npm:better-auth@1.7.7`, `npm:better-auth@1.7.7/db/migration`, `npm:kysely@0.29.6`,
   `npm:pg@8.23.1` (inline specifiers, no import map).
2. Build a `Kysely` over `PostgresDialect({ pool: new pg.Pool(...) })`; pass
   `database: { db, type: "postgres" }`.
3. Set `baseURL`, `basePath: "/api/auth"`, `secret` (≥32 chars), `trustedOrigins: [baseURL]`,
   `emailAndPassword: { enabled: true }`.
4. Run `getMigrations(auth.options)` then `runMigrations()` once at startup.
5. In `Deno.serve`, route `/api/auth/*` to `auth.handler(req)`. Authenticate other routes with
   `auth.api.getSession({ headers: req.headers })`.
6. Sign-up/sign-in: POST JSON with an `origin` header equal to `baseURL` (required by `trustedOrigins`). Read
   the session cookie from `response.headers.getSetCookie()`.

## Recommendation for MT-08

**Proceed with changes.**

- **Gate passes.** The go/no-go question resolves to GO on the evidence above. MT-08 does not need to fall
  back to API-keys-only on feasibility grounds.
- **Changes to plan the MT-08 spike with:**
  1. Pin `better-auth` at 1.7.7 (or whatever the builder confirms) with an inline `npm:` specifier. This spike
     used an import map only for convenience, and the final code must use inline specifiers.
  2. Use `getMigrations` from `npm:better-auth@1.7.7/db/migration`, not `better-auth/db`. Confirm the subpath
     when upgrading.
  3. Consider whether `Deno.serve`'s legacy-abort deprecation is a concern for the handler. The warning
     appeared in the run output but caused no failure here.
  4. **Decide token transport before build:** `plugins: [bearer()]` iff the CLI/tenant middleware will use
     `Authorization: Bearer <session token>` (without it the body token 401s); else forward the signed cookie.
     MT-10's e2e needs the same decision.
- **Review re-verification (Opus 5.5, 2026-10-11; reviewer's results, not Haiku's):** cookie attributes are
  HttpOnly, SameSite=Lax, 7-day lifetime, no Secure on plain-http loopback. Wrong password and unknown user
  both return 401 with an identical message (no user enumeration). Sign-out invalidates the session (200, then
  the cookie 401s). The vanilla `createAuthClient` works under Deno: sign-in succeeds and the token is
  captured in `onSuccess` — but the body token alone 401s without the `bearer()` plugin and 200s with it.
- **Not verified here, so MT-08 must check them:** (a) the `Secure` cookie attribute and `baseURL` handling
  behind a non-loopback or https deployment; (b) rate limiting and session expiry; (c) the full repo
  `deno task ci` pipeline with these deps (not run; the spike ran outside the repo); (d) whether `deno.lock`
  changes are produced when the spike is folded into the repo; (e) the transitive `@better-auth/telemetry`
  package (not checked); (f) Better Auth vs `pg` Pool compat — whether Better Auth accepts a postgres.js
  client or needs its own `pg` Pool (open from sq-10).
