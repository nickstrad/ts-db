# sq-04: k6 Output Format Comparison for DuckDB Ingestion

**Quest:** Which k6 output format is most convenient for DuckDB ingestion via `read_json_auto` / `read_csv_auto`?

**Testing date:** 2026-10-10  
**k6 version tested:** v0.52.0  
**DuckDB target:** Use `read_json_auto` for streaming ingestion into `k6_points` table

---

## Summary Recommendation

**Use `--out csv=logs/k6/<run-id>/raw.csv` for simplicity, or `--out json=logs/k6/<run-id>/raw.json` for precision.**

**CSV is recommended for `perf/ingest_k6.ts`** because `read_csv_auto()` consumes it directly with minimal preprocessing (no line filtering required). The trade-off: Unix-epoch timestamps (second precision) instead of nanoseconds, and many sparse columns for unused tags.

**JSON is viable if nanosecond precision matters** for joining against server-side events. Requires one filter step: `WHERE type = 'Point'` before ingestion to skip Metric definition lines.

---

## Format Comparison Table

| Aspect | JSON (`--out json=`) | CSV (`--out csv=`) |
|--------|---|---|
| **One metric point per line?** | ✅ Yes (Point type only) | ✅ Yes (one row per point) |
| **Flat tag structure** | ⚠️ Nested object (trivial to flatten) | ✅ Already flat columns |
| **Timestamp precision** | ✅ Nanoseconds (ISO 8601) | ❌ Seconds only (Unix epoch) |
| **Metadata lines** | ⚠️ Every metric has Metric definition line | ✅ None; header + data rows only |
| **Column count** | ✅ Dynamic (as many cols as in tags) | ❌ 19 fixed (many empty for unused tags) |
| **Empty cell handling** | ✅ Tags omitted if unused | ❌ Many empty columns per row |
| **DuckDB readiness** | ⚠️ Requires line filter (`WHERE type = 'Point'`) | ✅ Direct ingest via `read_csv_auto()` |
| **DuckDB schema inference** | ✅ Clean (tags → columns) | ⚠️ Many sparse columns (unused tags) |
| **File size overhead** | ⚠️ Larger (one JSON object per line) | ✅ Slightly smaller |
| **Ingestion complexity** | 🟡 Medium (one filter step) | 🟢 Low (direct `read_csv_auto`) |

## Named Gotchas

### Gotcha 1: Interleaved Metadata Lines in JSON
**Problem:** k6's JSON output interleaves `type: "Metric"` definition lines with `type: "Point"` data lines. DuckDB's `read_json_auto` will try to ingest both and infer a union type.

**Solution for `perf/ingest_k6.ts`:**
```sql
-- Filter to Point records only before ingestion
SELECT * FROM read_json_auto('logs/k6/<run-id>/raw.json') 
WHERE type = 'Point'
```

### Gotcha 2: Nested Tags in JSON
**Problem:** Tags are nested under `data.tags.*` as a flat object, not a top-level column.

**Solution:** `read_json_auto` handles nested objects and automatically unnests them into columns:
- Input: `data.tags.method = "GET"`
- Output column: `method` (VARCHAR)

No extra `unnest()` call needed; DuckDB infers the structure.

### Gotcha 3: CSV Timestamp Precision Loss
**Problem:** CSV format uses Unix timestamps in **seconds only** (e.g., `1791651241`), losing the nanosecond precision available in JSON (`2026-10-10T16:53:51.314934797Z`).

**Impact:** For joining k6 metrics against server-side events (which use nanosecond timestamps), CSV requires rounding/bucketing by second. JSON preserves full precision.

### Gotcha 4: CSV Column Explosion
**Problem:** k6 CSV creates a fixed 19-column header covering all possible tag combinations, even if many are unused:
- `check` — only populated for `checks` metrics
- `error`, `error_code` — only for failed requests
- `method`, `name`, `proto`, `status`, `url` — only for HTTP metrics

Result: Each row has many empty cells. For a large load test, this wastes ~40% of file size.

### Gotcha 5: Empty Tag Values in JSON
**Problem:** k6 includes tags with empty values (e.g., `"group": ""`). DuckDB will infer these as VARCHAR columns.

**Not a blocker:** Empty strings are queryable and don't break `read_json_auto`, but they add columns to the schema that may not be useful.

### Gotcha 6: ISO 8601 Timestamp Parsing
**Problem:** JSON timestamps are in ISO 8601 format with nanosecond precision (`2026-10-10T16:53:51.314934797Z`). This is **not a DuckDB issue** — it natively parses this format.

**Benefit:** Direct usability: `SELECT time::TIMESTAMP FROM k6_points WHERE time > '2026-10-10 16:53:00'::TIMESTAMP`

## DuckDB Ingestion Recipe

### For CSV (Recommended for `perf/ingest_k6.ts`)

```sql
-- Create the table
CREATE TABLE IF NOT EXISTS k6_points (
  metric VARCHAR,
  time TIMESTAMP,
  value DOUBLE,
  expected_response BOOLEAN,
  method VARCHAR,
  status INTEGER,
  url VARCHAR,
  scenario VARCHAR,
  check VARCHAR,
  run_id VARCHAR  -- Added column for this run
);

-- Ingest one k6 run (note: timestamp precision is limited to seconds in CSV format)
COPY k6_points FROM (
  SELECT 
    metric_name as metric,
    from_unixepoch(timestamp)::TIMESTAMP as time,
    metric_value as value,
    try_cast(expected_response as BOOLEAN) as expected_response,
    method,
    try_cast(status as INTEGER) as status,
    url,
    scenario,
    check,
    'run-2026-10-10-16-53' as run_id
  FROM read_csv_auto('logs/k6/run-2026-10-10-16-53/raw.csv')
);
```

### For JSON (If Nanosecond Precision Needed)

```sql
-- Use JSON if you need nanosecond-precision timestamps for joining with server-side event logs
COPY k6_points FROM (
  SELECT 
    metric,
    time::TIMESTAMP,
    value,
    expected_response::BOOLEAN,
    method,
    status::INTEGER,
    url,
    scenario,
    check,
    'run-2026-10-10-16-53' as run_id
  FROM read_json_auto('logs/k6/run-2026-10-10-16-53/raw.json')
  WHERE type = 'Point'  -- Skip Metric definition lines
);
```

## Implementation Notes for `perf/ingest_k6.ts`

**Recommended approach: Use CSV format for simplicity.**

1. **Use `--out csv=logs/k6/<run-id>/raw.csv`** when running k6 scenarios
2. **Load with DuckDB:** `read_csv_auto('logs/k6/<run-id>/raw.csv')`
3. **Map and add run_id:** Transform column names (e.g., `metric_name` → `metric`) and add run identifier in SQL
4. **Trade-off:** Unix-second timestamps (no nanosecond precision), but no line filtering needed

**If nanosecond precision is required** (for microsecond-level join with server-side events):
1. Use `--out json=logs/k6/<run-id>/raw.json` instead
2. Load with DuckDB: `read_json_auto(...) WHERE type = 'Point'`
3. JSON structure is already DuckDB-friendly after filtering Metric lines

**Do not:**
- Expect millisecond or microsecond precision from k6 metrics; the limit is the output format
- Mix CSV and JSON output formats in the same ingestion run

## Alternatives Considered (Not Recommended)

### InfluxDB Line Protocol (`--out influxdb=`, experimental)
- **Status:** Experimental in k6 0.52.0, not fully documented
- **Gotcha:** Requires a running InfluxDB server or a mock; not suitable for offline analysis
- **Verdict:** Not recommended for this use case

### k6 Cloud (`--out cloudapi`)
- **Status:** Requires k6 Cloud credentials
- **Gotcha:** Introduces external dependency; data leaves the droplet
- **Verdict:** Not applicable for local observability
