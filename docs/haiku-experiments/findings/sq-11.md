# sq-11: triage of lx-01's flaky property-test invariants

**Question.** lx-01 swept seeds 1–200 of the property suite: 182 clean, 18 failed. For each failing family, is
the defect in the GENERATOR or the INVARIANT, and is the failure a SEED-FLAKE (a rare bad draw from a healthy
generator) or SYSTEMATIC (the generator is structurally unlikely to satisfy the check at this budget)?

**Scope.** Read-only on `tests/`, `core/`, `platform/`, `sdk/`, `app/`, `scripts/`, `perf/`, `deno.json`. No
file under those paths was edited. Fix sketches below exist only in this file. Scripts written for measurement
are in `work-scripts/` and indexed in `work-scripts/INDEX.md`. Raw sweep and probe outputs are in
`sq-11-data/`.

### 1.2 Why full-board draws are rare (generator, read from code)

`reachableArb` = `playersArb × orderArb`, with `orderArb` = a shuffled subarray of random length 0..9, then a
shuffled permutation of that subarray (`tests/property/rules_test.ts`, `orderArb`). A full-board draw needs
**all nine moves played with no line held**. Two things cut that down:

- Only the length-9 orders can fill the board. The length is one of ten values, and fast-check does not weight
  it evenly (measured below).
- Among the 9! = 362,880 full orders, most end in a win before move 9. Enumerated exactly
  (`work-scripts/deno/sq-11-rules-reachable-probe.ts`, section 4):

```
exact over all permutations of 9 cells (362880):
  draws (full board, no line) = 46080  -> 0.12698 of length-9 orders
  won before move 9           = 316800
```

So only 12.7% of full orders reach a draw, and 87.3% end earlier in a win.


- Per sample: P(full-board draw) = 0.92%. Expected draws in 300 samples ≈ 2.75.
- Per seed: 129 of 2000 seeds (6.45%) have zero. Poisson(2.751) predicts 6.39%. The per-seed count is
  Poisson-shaped, so the failure rate is set by the mean hit count, not by a few bad seeds.
- lx-01's 10/200 (5%) and the 1–200 subset (10/200) are inside this rate.

Note on the 100k-sample figure: a single 100k-sample run (seed 1) gave P(len 9) = 0.083 and P(draw) = 0.011.
That is _not_ the rate of the first 300 runs. fast-check's bias frequency depends on the run index
(`runIdToFrequency`, `fast-check` `lib/fast-check.js:1122`, used via `streamSample` → `toss` at `:2672–2683`).
The 300-run measurement above is the one that applies to the test. An earlier estimate built on the 100k
figure (about 3.7% zero-seeds) was wrong, and is superseded by the 2000-seed count.

### 1.4 Verdict and fix sketch

**Verdict: GENERATOR defect, SYSTEMATIC at budget 300.** The assertion is a legitimate coverage requirement.
The generator produces its event (a full-board draw) at 0.92% per sample, so the test's 300-sample budget only
expects 2.75 hits, and it fails at the Poisson-zero rate (6.4%). This is not a rare bad draw from a healthy
generator; the generator is structurally weak on this event.

**Sketch (not applied; `tests/` is read-only for this quest).** The minimal fix biases the generator so
length-9 orders are common. The assertion itself stays unchanged. This candidate was measured in the probe
(`candidateOrderArb`, `work-scripts/deno/sq-11-rules-reachable-probe.ts`):

```ts
// tests/property/rules_test.ts — SKETCH ONLY
const prefixOrderArb = fc.shuffledSubarray(CELLS, { minLength: 0, maxLength: 9 }).chain((cells) =>
  fc.shuffledSubarray(cells, { minLength: cells.length, maxLength: cells.length })
); // today's orderArb, renamed
const fullOrderArb = fc.shuffledSubarray(CELLS, { minLength: 9, maxLength: 9 });
const orderArb = fc.oneof(
  { weight: 1, arbitrary: prefixOrderArb },
  { weight: 1, arbitrary: fullOrderArb }, // every full order is still a legal play prefix
);
```

Measured effect (`[candidate]` lines of `rules-probe-1-2000.txt`):

```
[candidate] across 2000 seeds x 300 samples: P(len 9)=0.53576, P(full-board draw/sample)=0.06782, mean draws/seed=20.345
  seeds by draws-in-300: {"6":1,"7":2,...,"36":1}
```

Across 2000 seeds, 0 seeds have zero full-board draws (the lowest per-seed count was 6, and the mean is 20.3).
The sweep summary line for the candidate was `no-full-board-draw at 0 (0.0%)`.

Two things to check before applying this (both _not executed_, see the list at the end):

- `orderArb` is shared by the other rules properties, so their coverage also shifts (more full boards, fewer
  mid-game states). These properties are universal, so they should still hold, but this was not run against
  the suite.
- A deterministic anchor would also help, since it does not depend on the generator's mixing at all. This
  order was checked through `applyMove` (`rules-probe-1-2000.txt`, section 5):

```
anchor order [0,1,2,4,3,5,7,6,8]: status=draw winner=null board=XOXXOOOXX
```

Add it as an `example` next to the property, so the "a draw exists" claim holds even if the generator changes.

- Under a normal fit (mean 43.7, sd 8.2), P(< 25) ≈ 1.1%, so about 2.2 failures are expected in 200 seeds.

about two standard deviations below the typical count, so a ~1% tail of seeds falls below it. This is not an

**Sketch (not applied).** Lower the floor to match the observed distribution, e.g. `stickyDeduplicated: 15`.
The lowest value in 200 seeds is 22, and 15 is about 3.5 sd below the mean (normal-fit estimate, _not
executed_). A more principled option is to scale the floor with `numRuns`, e.g. ≈0.075 per run. Lowering a
floor weakens the coverage guard, so the owner should decide; I'm giving the number, not making the call.

### 3.3 Verdict

**SEED-FLAKE (a tail zero).** The event is generated about 6.3 times per 300-sample set, and seed 24 is the
only seed with zero. For Poisson(6.34), P(0) = 0.18% and the expected number of zero-seeds in 200 is 0.35; one
observed is consistent with that. The generator is not structurally weak here.

One structural note, which is generator design rather than a defect: the equality path comes almost entirely
from the `tight` profile (1246 of 1269 equality samples). The `exact` profile never produces it, since the cap
is set to the starting total, so no pruning happens. The `wide` profile contributes 23.

**Sketch (not applied; reasoned from `core/logging/rotation.ts` lines 257–268, not executed).** If the owner
wants the equality path less dependent on one profile, add a `boundary` profile: set `maxTotalBytes` to the
on-disk total minus the bytes of the oldest non-today directory (when that is > 0). `plan` prunes oldest-first
until `total <= cap`, so that directory's removal lands exactly on the cap. This would make the event
deterministic, not a sampling hit.

**Verdict: intermittent, not deterministic.** 187: 2 of 3 runs crashed. 14: 0 of 3 (the lx-01 crash did not

entry in `dmesg` is consistent with a bad function pointer (a jump to address 1), which points to memory
corruption in a native callee. That is a hypothesis for sq-07, not a finding.
