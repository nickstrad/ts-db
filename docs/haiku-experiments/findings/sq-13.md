# sq-13: Tenant-routing threat-model review of `docs/plans/multitenancy.md`

**Scope.** Plan review only. Read: `docs/plans/multitenancy.md` in full (MT-01…MT-10, §1, §2.1, §4) and the item-15/config/auth/router code it builds on. Nothing was run: no tests, no property suites, no exploit attempts. Every vector below is reasoned from plan text and read code. Code citations are `file:line` in this worktree (branch `haiku/sq-13`, based on `main` at e423ed1). "Plan omission" means the plan is silent on the point, so the defense is absent by default.

## Summary

The plan's core isolation rule is sound on paper: tenant identity comes from the credential, the client never names a tenant, and a cross-tenant doc id must look like a missing one (§1 "load-bearing rule"; MT-07). Credential-derived identity, forged-header rejection, literal `../x` rejection, and key-at-rest hashing are all covered by named acceptance criteria. Those are the families the plan actually tested for.

The gaps are in the seams the plan leaves open. The headline is that the plan never specifies **how the tenant context reaches concurrent fibers**, and **what happens when it is absent**. Those two choices decide whether the isolation rule holds under concurrency, and no planned test would detect a wrong choice. The next tier is revocation: a cached credential stays valid for an unspecified window, and nothing in the plan bounds it. Then come the representation and filesystem seams: `StorageLocation` is an open type, so the "by construction" traversal guarantee holds only inside `resolve`; a string-distinct but UUID-identical id splits one tenant across two files; and `prepare` follows symlinks.

**Headline: 1 Critical, 4 High, 14 Medium, 9 Low gaps** (counted in the table below), plus covered families listed in the coverage section.

## Top 3 gaps

### 1. Shared-context cross-tenant bleed (Critical, latent, conditional)

**Plan location:** MT-07 work item 1 (line 305-307: "inject `TenantContext { tenantId }` into the Effect layer"); MT-04 (line 251-252: "via a `TenantContext` tag in the Effect layer").

**Prerequisites.** `TENANCY=api-key`. The server is built with one shared layer or a mutable `Ref` holding the current tenant, instead of per-request provision. Two tenants (A and B) each have a live key. Item 15's per-file `Semaphore(1)` is in the path, so a request can wait, which is a yield point.

**Steps.**
1. A's request passes the middleware and sets the shared context to A. It then waits on the write queue (`platform/sqlite.ts:241`).
2. B's request passes the middleware and sets the shared context to B.
3. A's queued write resumes and reads the shared context. It now sees B, and writes into B's file, or reads B's document under A's identity.
4. Both responses are 200. Nothing returns 401 or 404, so nothing in the request path flags the mismatch.

**Impact.** Silent cross-tenant write, and cross-tenant read, under concurrent load. This breaks the plan's load-bearing rule (§1 line 49-51) with no error signal.

**Why the plan misses it.** The MT-07 acceptance tests (line 313-316) are sequential: create two tenants, request across them, forge a header. The MT-04 concurrency test (line 262-263) and the MT-09 concurrency property (line 372-374) drive the router and registry seam with explicit tenant arguments, not the middleware. A correct test harness and a broken middleware can both pass. The plan states the seam ("Effect layer") without saying per-fiber or per-request.

**Plan tightening (no fix sketch).** MT-07 must state that tenant context is per-request and per-fiber, not shared. It must require an end-to-end concurrency test through the HTTP middleware with interleaved tenants, where each tenant's writes queue behind the same semaphore that holds the other tenant's request. MT-09 must say whether its concurrency property runs through the middleware or only the seam.

### 2. Latent fail-open to the legacy single file (High)

**Plan location:** MT-04 (line 252-253: "The single-file path remains for the pre-tenancy default"); MT-07 (line 306-307: "Every `Storage` access resolves through it"); MT-02 (line 188-189: "`api-key` … enforced on `/apps/*`").

**Prerequisites.** `TENANCY=api-key`. A deployment upgraded from `off` still has its pre-tenancy data in the single-file database (MT-04 line 252: "back-compat for existing deployments"). A `Storage` call happens with no `TenantContext`: a background fiber (the backup scheduler, or the log sink flush), a route added outside `/apps/*`, or a request that bypasses the middleware.

**Steps.**
1. The call reaches `Storage`. No context is present.
2. The plan does not define what chooses the path in that case. If the implementation falls back to the single-file path, the call opens the legacy database.
3. Any caller that can reach that call reads or writes the legacy data, which is shared across tenants by definition.

**Impact.** Pre-tenancy data becomes reachable from api-key mode by any caller that lacks a tenant context. For an upgraded deployment this is every row that predates tenancy.

**Why the plan misses it.** The plan treats the single-file path as a mode, not as a fallback. MT-02 selects the mode by `tenancyMode`, but MT-04 also keeps the path reachable from `Storage` without a mode check. No acceptance test calls `Storage` with the context absent.

**Plan tightening.** The plan must state that in `api-key` and `better-auth` modes, `Storage` with no `TenantContext` is a typed failure, never a default path. It must add an acceptance test for that case, and must say which background tasks run under which context.

### 3. Revocation and deactivation window bounded by an unspecified TTL (High)

**Plan location:** MT-07 work item 1 (line 306: "with a short TTL cache"); MT-07 acceptance (line 315: "revoked key → 401"); MT-05 (line 275-277: `DELETE` keys and tenants); MT-06 acceptance (line 292-293: "deactivate → all keys 401"); MT-02 (no TTL row, line 181-190).

**Prerequisites.** A tenant key K is leaked, for example through a CI log, a shell history, or a pasted snippet. The operator revokes K, or deactivates the tenant, through MT-05 or MT-06.

**Steps.**
1. K is used at time t0. The middleware caches the positive result with TTL T.
2. The operator revokes K at time t1. Postgres now says revoked (`resolveTenantByKeyHash` rejects it, MT-03 line 214-215). The cache is not invalidated.
3. Requests with K succeed until t0 + T, or longer if the TTL slides on access. Each server process holds its own cache, so the window applies per instance.
4. The same applies to deactivation (5.2): every key of the tenant keeps working for the window.

**Impact.** The plan's incident response is "revoke, then wait", and the wait is undefined. A sliding TTL with an active attacker makes the window unbounded. A multi-instance deployment widens it.

**Why the plan misses it.** The plan's own acceptance text says "revoked → 401" with no time bound. MT-10 scenario 7 (line 515-517) bounds the wait by "the configured TTL plus 1 s", but no config row exists for that TTL (MT-02 lists none), so the bound the e2e test uses has no definition. The plan has no invalidation mechanism, though Postgres provides `LISTEN/NOTIFY` for exactly this, and does not mention it.

**Plan tightening.** The plan must add a TTL config row to MT-02 with a default and an upper bound, state whether the TTL is fixed or sliding (fixed), and require that revocation and deactivation evict the cached entry on the same process. It must also state the window for other instances, or require cross-instance invalidation.

## Next tier (not in the top 3)

- **4.1 + 4.2: symlink and TOCTOU in `tenantsDir`** (Medium). Cross-tenant access through a planted link needs local write, but the plan has no symlink rule and no `realpath` check. The MT-09 containment property is lexical, so it cannot detect this.
- **9.1 + 9.2: no tenant backup, and a backup endpoint that reports success on the wrong file** (High and Medium). The data-loss path is the largest non-security risk in the plan, and the false-success endpoint makes it worse.
- **4.3: `StorageLocation` is open** (Medium). The "impossible by construction" claim holds only inside `resolve`.
- **2.1: uppercase UUID splits one tenant across two files** (Medium). The MT-09 isolation property treats the split as correct, so the property cannot catch it.

## Coverage argument

The families below are judged covered because the cited passages name a concrete defense and, where noted, an acceptance test.

**A1. Cross-tenant data access by the client.** The client never names a tenant. §1 line 49-51 says so as the load-bearing rule. MT-07 work item 2 ignores `x-tenant-id` and body tenant fields (line 308-309). MT-07 acceptance tests a forged header (line 316). MT-04 gives `Storage` no tenant parameter (line 251-252), so a body field cannot reach storage. The only residual risk is the warn-log channel (7.1). The shared-context gap (Top 1) is a separate family, about the server's own concurrency, and is not covered.

**A2. Cross-tenant doc-id enumeration.** A key holder asking for another tenant's doc id gets the same not-found as for a missing id. MT-07 acceptance (line 313-314) and MT-10 scenario 4 (line 483-487) both test this. Because the request is routed by credential, it never touches the other tenant's file, so there is no timing channel to probe.

**A3. Literal path traversal.** `../x` is rejected by `resolve` (MT-04 line 264). MT-09 generates malformed ids and requires either a typed error or containment (line 366-368). The gaps in this family (1.2 to 1.6) concern encodings and representations the plan does not enumerate, not the literal form.

**A4. Credential forgery, collision, and key-at-rest.** The key is `tsdb_` plus 32 random bytes, and only the SHA-256 hash is stored (MT-03 line 212-214). A cache collision or a hash-to-key recovery attack is not feasible at 256 bits. The plan omits the CSPRNG name, which is an open question (10.6), not a gap in the defense.

**A5. Admin-token separation.** Tenant keys are rejected on `/admin/*` because every admin route is behind `ADMIN_TOKEN` (MT-05 line 276-277), compared in constant time (`platform/http/auth.ts:40`).

**A6. Key-status oracle.** Unknown, revoked, and deactivated keys all return 401 (MT-07 line 315). The response does not reveal which case applied, and a key holder can only probe with a key they already hold.

**A7. Mode downgrade.** `TENANCY=off` leaves the request path unchanged (MT-02 line 186-188). The unresolved part is what `Storage` receives when the context is absent (6.3), which is partial, not a bypass.

## Open questions for the builders

These are ambiguities that MT-04 and MT-07 must resolve in code and tests. Each one changes a verdict above.

1. **What does "validated uuid" mean?** MT-04 line 245 says both "validated uuid" and "assert: no `..`, no separators". Pick one. A strict canonical parse, with lowercase output and rejection or normalization of any other form, closes 1.2 to 1.6 and 2.1. A blacklist closes none of them. State which.
2. **Is `TenantId` a parsed, branded type?** If it is a plain `string`, nothing enforces validation at the type level, and any caller can construct one. Should `StorageLocation` also be opaque, constructible only by `resolve`? (4.3)
3. **Where is the admin `:id` decoded?** Before or after validation? Is `%2e%2e%2f` rejected by the same rule as `../x`? (1.2)
4. **What does `tenantsDir` normalization require?** Must it be absolute, resolved, non-empty, not `/`, owned by the service user, and disjoint from other data directories? MT-02 has no acceptance row for it. (3.1, 3.2)
5. **Does `prepare` open files with no-follow semantics?** Is there a `realpath` containment check at open time, and is the file created with `O_EXCL`? Are sidecar files covered by the same rule? (4.1, 4.2)
6. **What is the TTL?** Default value, upper bound, fixed or sliding, and where it is configured. Add it to MT-02's table. (5.1)
7. **How is revocation propagated?** Eviction on the same process, and cross-instance invalidation through `LISTEN/NOTIFY` or a bounded window. State the window for each instance. (5.1, 5.2)
8. **Is negative lookup cached?** Is there a cap on cache entries, and is there any rate limit on unauthenticated requests? (5.3)
9. **How is `TenantContext` provided?** Per request, per fiber, or shared? Which background fibers run with which context? (6.2, 6.1)
10. **What happens when `Storage` has no `TenantContext`?** A typed failure, a default tenant id, or the single-file path? The plan must pick one. Only the first is safe in `api-key` and `better-auth` modes. (6.1, 6.3)
11. **How is the single-file path selected in each mode?** Is it a mode decision made once at startup, or a per-call fallback? (6.1)
12. **Does `prepare` single-flight the per-tenant handle?** Is the bounded `Map` get-or-create memoized so that two concurrent first requests share one handle? (8.1)
13. **Is an in-use handle ever evicted?** Is there a refcount or lease, and does eviction wait for in-flight requests? (8.3)
14. **What counts as a "tenant field in the body"?** Which spellings are ignored and logged? (6.4)
15. **Are `x-tenant-id` values escaped, truncated, or length-capped before logging?** Does `scripts/logs.ts` print values raw? Is there a volume limit on warn lines per client? (7.1, 7.2)
16. **Is the plaintext key excluded from every log and trace sink?** Specifically the `POST /admin/tenants` response body and the CLI output. (7.3)
17. **What backs up tenant data?** Until §4's per-tenant backup lands, should api-key mode refuse to start, or warn loudly? Should `POST /admin/backup/<app>` refuse, rather than succeed on the legacy file, in api-key mode? (9.1, 9.2)
18. **Does reactivation restore keys?** If yes, is that intended? If no, must deactivation also revoke keys, or must reactivation require re-issuing? (9.3)
19. **Does a session bind to one tenant?** With memberships in several tenants, which tenant does a session resolve to, and by what rule? Is there an unlink or revoke path, and is `role` enforced anywhere? (10.3)
20. **Which CSPRNG generates the key bytes?** MT-03 says "32 random bytes" without naming the source. (10.6)
21. **Are admin inputs parameterized?** Does the driver use tagged templates or string building for `name`, `slug`, and `:id`? (10.2)
22. **What does MT-09's containment property use?** Lexical normalization or `realpath`? And is the isolation property over parsed UUIDs rather than strings? (2.1, 4.1)
23. **Is the Postgres error text sanitized in admin 500 responses?** (7.4)
