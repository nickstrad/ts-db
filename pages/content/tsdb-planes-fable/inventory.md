## Fable modifications (the patch)

Each F-decision realises one M of the comparison document; "Where" names what changed in the bundle. M1 and M5
alter contracts Astra reviewed and passed in DP-01, so they are proposals needing Nick's word and a re-review,
not settled design.

- **F1 / M1 — route grants with a TTL.** New component `grant-cache` (data plane) and document
  `doc-grant-cache`; relationships `dp-grant` (authorization ↔ cache) and `dp-revoke` (router → cache, best
  effort); relabelled `dp-route`, `dp-forward`, `dp-owner`, `c-resolve`, `c-forward`. The DP-01 availability
  table ("online one-request decision, no reuse") is replaced in `doc-node-admission`, `doc-placement-router`,
  `doc-flow-move-database` and `doc-flow-move-failed` by the grant table (row "Authority unavailable, running
  agent" → "existing grants serve until their TTL; no new grants"). `flow-query-right-node` is the grant-miss
  path, new `flow-query-grant-reuse` is the steady state with no control-plane call, and `flow-query-stale`
  states that a stale-route retry obtains a **fresh decision** bound to the new epoch (closing the re-review's
  residual nit). The agent's check of grant epoch/generation against its durable local ACTIVE state remains
  the enforcement point; there is no lease and no clock in the fencing argument. Term `term-route-grant`.
- **F2 / M2 — build order.** Document `doc-build-order` (on `planes-context` and `planes-lane-components`):
  in-node half first on one VM keyed by database_id, then schema + default database, then gateway + grants +
  forwarder, then lifecycle/backup/recovery; the lanes acceptance tests re-targeted to databases and the 4.1
  ms / +2 ms gate. No diagram change: sequencing is not architecture.
- **F3 / M3 — the lane view inside the agent.** New component view `planes-lane-components` (scope `lanes`,
  child of `planes-agent-components`) importing the lanes proposal's lane components re-keyed by database:
  `lane-ipc`, `lane-scheduler` (mixed: Semaphore(1) per file and WRITER_QUEUE_CAP are landed), `lane-handles`
  (mixed: the 64-entry leased cache is landed), `lane-request-ids`, `lane-snapshot` (new: backups on a
  read-only connection, off the writer lock; today `Storage.snapshot` runs on the writer queue), plus the
  carried `classifier`, `execution`, `deadline`. Relationships `ln-*`. Lane assignment is tenant-affine by
  default and placement may pin a database to a lane (noted in `doc-node-admission`, `doc-metadata`,
  `doc-lanes`). `doc-lane-measurements` carries the lanes PoC numbers with provenance and the statement that
  they do not measure this design. The lanes logger / JSONL are deliberately not imported: observability stays
  omitted as in DP-01 DP10.
- **F4 / M4 — default database and selection surface.** `doc-ingress`, `doc-authorization`,
  `doc-placement-router`, `doc-caller`, `doc-database-registry` gain the selection contract: `database` option
  per session or per call, tenant-scoped name, none → reserved `default`, name → immutable ID resolved under
  the trusted tenant and stamped into the operation IR after authorization; the classifier and agent never see
  a name. Migration: each existing tenant file becomes its tenant's `default` (minted ID, placement row owner
  = the one node, epoch 1); `ControlPlaneRouter` becomes `resolve(databaseId)` with `TenantContext` extended.
  Schema question: Fable's default is a per-database schema fingerprint, not yet decided. Term
  `term-default-database`. Step 1 of the query flows names the default.
- **F5 / M5 — VM loss end to end.** New person `platform-operator` and external system `provider`;
  relationships `ctx-attest`, `ctx-provider`, `c-attest`, `c-provider`, `cp-attest`, `cp-recover`,
  `cp-suspect`, `cp-provider`, `cp-backup-delete`. Flows `flow-recover-from-loss` (detection → attestation →
  provider proof recorded → per database CAS to FENCED-BY-OPERATOR at a fresh epoch → restore from the latest
  recorded manifest onto an eligible VM → verify → CAS ACTIVE → activate), `flow-recover-refused` (no
  attestation → refused; databases stay unavailable) and `flow-drop-lost-agent` (lifecycle identity deletes
  backup objects only once the VM is attested lost). Standing rule in every one of them: inability to contact
  the old writer is never permission to activate a copy. Recovery point is the backup interval; this is not
  automatic failover. Term `term-attestation`. DP-01 tweak 6's deferral text is replaced by a closure note in
  `doc-backups`, `doc-lifecycle-policies`, `doc-planes-control-components`, `doc-flow-drop-database`,
  `doc-flow-drop-failed`.
- **F6 / M6 — backup completion as a recorded manifest.** New component `backup-registry` (control plane),
  relationships `cp-manifest`, `cp-manifests-sql`; flows `flow-backup-manifest` (snapshot off the writer lock
  → immutable PUT → read-back verify → acknowledgement carries the manifest → recorded, keyed by (database ID,
  generation) → eligible for restore) and `flow-backup-unverified` (no manifest, not a candidate). Term
  `term-backup-manifest`. The landed pipeline in `platform/backup.ts` is the mechanism, re-keyed.
- **F7 / M7 — instance-level move diagrams.** `flow-move-instances` and `flow-move-failed-instances` (children
  of `planes-deployment`, linked from the logical move flows and back) with instance participants
  `dep-control`, `dep-metadata`, `dep-a-agent`, `dep-b-agent`. New instance relationship
  `dep-a-agent-to-dep-b-agent` for the A → B snapshot stream, following the lanes dataset's P16 node-to-node
  forward: an instance edge with no container-level self-relationship and therefore no `modelRelationshipId`
  (the only deployment-tier edge without one; every other `dep-*` edge still names its logical relationship).
  c4-sdk permits deployment instances only in deployment views, so the companions are illustrative deployment
  views (not dynamic step trees) whose documents and this inventory carry the ordered sequence; the step trees
  stay on the logical flows. The DP-01 repair's checkpoint ordering is kept step for step. DP-01 tweak 7's
  deferral text is replaced by a closure note in both logical move documents.
- **F8 / M8 — candidate v1 placement rule, pending Nick's decision.** New component `placement-policy`
  (control plane) and relationship `cp-policy`; two steps inserted into `flow-create-database`. Its documents
  say **proposed, pending Nick's decision** and that the registry keeps placement policy OPEN until he
  decides; the addendum's prohibition on inventing a solved mechanism is respected by labelling, not by
  omission. Rule: among eligible VMs, lowest descriptor-weighted load (capacity nofile − reserve; 3
  descriptors per writer, 2 per pooled reader; size tiebreak); weights and locality open.
- **F9 — sources and pins.** Every carried-over source is re-pinned to `main` at `3d25004` (all paths exist
  there; nothing under `core/`, `platform/` or `sdk/` changed since `2d30330`). DP-01's brief, addendum and
  review are `src-dp01-*`; `src-brief` is the DP-02 brief at its own commit `b2b65b0`; the DP-01 addendum
  needs no SHA-256 special case because it is now on `main`. Every element, relationship, diagram and document
  also cites `src-planes` and `src-comparison`.
- **F10 — mixed-tier edge numbers.** Fable flows that mix container-tier `c-` and component-tier `cp-`
  relationships (backup and recovery) show a container edge as 100 + its container number so per-diagram
  display numbers stay unique while remaining model references; `c-node-backup` is also drawn that way in the
  control-plane view. Carried-over diagrams keep DP-01's numbers.
- **F11 — what did not change.** Registries, epoch-checked and per-database serialised lifecycle commands, the
  trust boundary, bounded scheduling keyed by database with tenant/VM ceilings, the offline move protocol and
  its fencing rule, drop/tombstone semantics, status marking (`existing` classifier/execution, `mixed`
  deadline/placement-router, all processes `planned`) and the illustrative deployment are carried over
  unchanged. The three existing datasets and their content trees are byte-identical to `main`.

## Terms

| ID                      | Term                  | Definition                                                                                                                                                                                                                                                                              |
| ----------------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `term-route-grant`      | route grant           | A time-boxed, revocable record the control-plane routing authority issues to a gateway for one database: owner VM, epoch, generation, grant version and TTL. The gateway reuses it across requests until it expires, WrongOwner invalidates it or a grant-version bump revokes it (M1). |
| `term-default-database` | default database      | The reserved database named default that every tenant has; a request that names no database gets it. Each existing tenant file becomes its tenant's default database at migration (M4).                                                                                                 |
| `term-backup-manifest`  | backup manifest       | The recorded completion record of one backup, keyed by (database ID, generation): object key, checksum, format and completion state. Only a recorded manifest makes a backup a restore candidate (M6).                                                                                  |
| `term-attestation`      | isolation attestation | A platform operator's statement, backed by a recorded provider-API response, that a lost VM is powered off or network-detached. It is the precondition for activating any copy of a database the VM hosted (M5).                                                                        |
